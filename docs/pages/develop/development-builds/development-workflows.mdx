Development builds permitem iterar rápido. Além disso, você pode ampliar os recursos do seu development build para oferecer uma melhor experiência de desenvolvimento ao trabalhar em equipe, ou personalizar o build de acordo com suas necessidades.

## Ferramentas

### URLs de tunnel

Às vezes, condições de rede restritivas dificultam a conexão com o servidor de desenvolvimento. O comando `npx expo start` expõe seu servidor de desenvolvimento em uma URL pública, acessível através de firewalls do mundo todo. Essa opção é útil quando você não consegue se conectar ao servidor de desenvolvimento pela opção LAN padrão ou quando quer receber feedback sobre sua implementação enquanto desenvolve.

Para obter uma URL de tunnel, passe a [flag `--tunnel`](/more/expo-cli/#tunneling) para o `npx expo start` pela linha de comando.

### Atualizações publicadas

O comando `eas update` do EAS CLI empacota o estado atual dos seus arquivos JavaScript e de assets em uma "atualização" otimizada. Essa atualização fica armazenada em um serviço de hospedagem da Expo. Um development build do seu app pode carregar atualizações publicadas sem precisar fazer checkout de um commit específico nem deixar uma máquina de desenvolvimento ligada.

### Informar a URL de uma atualização manualmente

Quando um development build é aberto, ele mostra uma interface para carregar um servidor de desenvolvimento ou para "Enter URL manually" (informar a URL manualmente). Você pode informar manualmente uma URL que abre uma branch específica. A URL segue este padrão:

```text
https://u.expo.dev/[your-project-id]?channel-name=[channel-name]

# Example
https://u.expo.dev/F767ADF57-B487-4D8F-9522-85549C39F43F?channel-name=main
```

Para obter o ID do seu projeto, use a URL do campo [`expo.updates.url` da app config](/versions/latest/config/app/#url). Para ver a lista de canais, execute `eas channel:list`.

### Deep linking para a URL de uma atualização

Você pode carregar seu app em um aparelho que tenha um development build compatível abrindo uma URL de inicialização com o parâmetro de query `__expo_url`. No SDK 58 e posteriores, a URL tem a seguinte forma:

```text
{scheme}://?__expo_url={manifestUrl}
```

| parâmetro     | valor                                                                                                                                     |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `scheme`      | Esquema de URL do seu client (o padrão é `exp+{slug}`, em que o [`slug`](/versions/latest/config/app/#slug) é o valor definido na app config) |
| `manifestUrl` | URL codificada de um manifesto de atualização a carregar. A URL será `https://u.expo.dev/[your-project-id]?channel-name=[channel-name]`         |

Exemplo:

```text
exp+app-slug://?__expo_url=https%3A%2F%2Fu.expo.dev%2F767ADF57-B487-4D8F-9522-85549C39F43F%2F%3Fchannel-name%3Dmain
```

No exemplo acima, o `scheme` é `exp+app-slug`, e o `manifestUrl` é um projeto com o ID `F767ADF57-B487-4D8F-9522-85549C39F43F` e o canal `main`.

`__expo_url` é um dos parâmetros de query reservados do launcher, que começam com `__expo_`. O launcher trata qualquer URL que tenha pelo menos um parâmetro `__expo_*` antes de a URL chegar ao seu app. Todos os parâmetros reservados são opcionais e independentes. O launcher os remove antes de o app receber a URL, então eles nunca chegam ao tratamento de deep links do seu app nem ao servidor de desenvolvimento.

| parâmetro                      | valor                                                                                                   |
| ------------------------------ | ------------------------------------------------------------------------------------------------------- |
| `__expo_url`                   | URL codificada do projeto ou do manifesto de atualização a carregar.                                    |
| `__expo_disable_onboarding=1`  | Pula a tela de introdução que aparece na primeira abertura de um development build depois da instalação. |
| `__expo_disable_fab=1`         | Oculta o botão Tools (o botão flutuante que abre o menu do desenvolvedor) nesta abertura.               |
| `__expo_disable_auto_launch=1` | Impede que o menu do desenvolvedor abra quando o app inicia, nesta abertura.                            |

`__expo_disable_fab` e `__expo_disable_auto_launch` valem apenas para o processo iniciado e nunca alteram as configurações salvas do menu do desenvolvedor. Quem abrir o app depois ainda verá o menu e o botão Tools. Os parâmetros antigos `disableFab=1` e `disableAutoLaunch=1` continuam atualizando as configurações salvas.

Os mesmos parâmetros funcionam em URLs de inicialização do Expo Go, por exemplo `exp://192.168.1.10:8081?__expo_disable_auto_launch=1`.

> **info** O SDK 57 e anteriores aceitam apenas a forma antiga `{scheme}://expo-development-client/?url={manifestUrl}`. A forma antiga e seus parâmetros `disableOnboarding=1`, `disableFab=1` e `disableAutoLaunch=1`, colocados junto de `url`, continuam funcionando no SDK 58 e posteriores, em que o `npx expo start` gera a forma `__expo_url`.

#### Usar URLs de inicialização em cenários de automação

Ao abrir um development build com automação, como em um workflow de CI/CD, em um teste end-to-end ou em um loop de agente, adicione `__expo_disable_onboarding=1`, `__expo_disable_fab=1` e `__expo_disable_auto_launch=1` à URL de inicialização. Defina `EXPO_NO_DEV_MENU=1` ao iniciar o Expo CLI para adicionar esses parâmetros a todas as URLs de inicialização, QR codes e redirecionamentos dessa sessão. O Expo CLI faz isso por padrão quando não é interativo, como em CI ou sem TTY. Defina `EXPO_NO_DEV_MENU=0` para desativar.

#### Deep links específicos do app

Ao testar deep links no seu development build, por exemplo ao navegar até uma tela específica de um app Expo Router ou ao testar o redirecionamento de volta ao app durante um fluxo de login OAuth, monte a URL exatamente como montaria para abrir um deep link em um build standalone do seu app (por exemplo, `myscheme://path/to/screen`).

O projeto precisa já estar aberto no development build para que um deep link específico do app funcione. Abrir o development build a frio com um deep link específico do app não é possível no momento. Evite usar `expo-development-client` no caminho dos seus deep links específicos do app, pois é um caminho reservado usado para abrir uma URL atualizada.

### QR codes

Você pode usar nosso endpoint para gerar um QR code que um development build carrega facilmente.

Requisições enviadas para `https://qr.expo.dev/development-client` com parâmetros de query como `appScheme` e `url` recebem como resposta uma imagem SVG com um QR code, que pode ser escaneado facilmente para carregar uma versão do seu projeto no development build.

| parâmetro   | valor                                                                                                                                                                    |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `appScheme` | Esquema de deep link codificado em URL do seu development build (o padrão é `exp+{slug}`, em que o [`slug`](/versions/latest/config/app/#slug) é o valor definido na app config) |
| `url`       | URL codificada de um manifesto de atualização a carregar. A URL será `https://u.expo.dev/[your-project-id]?channel-name=[channel-name]`                                        |

Exemplo:

```text
https://qr.expo.dev/development-client?appScheme=exp%2Bapps-slug&url=https%3A%2F%2Fu.expo.dev%2FF767ADF57-B487-4D8F-9522-85549C39F43F0%3Fchannel-name%3Dmain
```

No exemplo acima, o `scheme` é `exp+app-slug`, e o `url` é um projeto com o ID `F767ADF57-B487-4D8F-9522-85549C39F43F` e o canal `main`.

## Exemplos de workflows

Estes são alguns exemplos de workflows para ajudar sua equipe a aproveitar ao máximo o seu development build. Se você tiver outros que seriam úteis para outras equipes, [envie um PR](https://github.com/expo/expo/tree/main/CONTRIBUTING.md#-updating-documentation) para compartilhar seu conhecimento!

### Prévias de PRs

Você pode configurar seu processo de CI para publicar um Expo Update sempre que um pull request for atualizado e adicionar um QR code usado para ver a mudança em um development build compatível.

Veja as [instruções para publicar prévias de apps em pull requests](/eas-update/github-actions/#publish-previews-on-pull-requests) para implementar esse workflow no seu projeto usando GitHub Actions, ou para usar como modelo no CI de sua escolha.

## Extensões

As extensões permitem ampliar seu development client com recursos adicionais.

### Ampliando o menu do desenvolvedor

O menu do desenvolvedor pode ser ampliado com botões extras usando a API `registerDevMenuItems`:

```tsx
import { registerDevMenuItems } from 'expo-dev-menu';

const devMenuItems = [
  {
    name: 'My Custom Button',
    callback: () => console.log('Hello world!'),
  },
];

registerDevMenuItems(devMenuItems);
```

Isso cria uma nova seção no menu do desenvolvedor com os botões que você registrou:

## Defina o runtimeVersion na app config

Quando você cria um development build do seu projeto, você ganha um ambiente estável para carregar qualquer mudança no app definida em JavaScript ou outras mudanças relacionadas a assets. Outras mudanças no app, seja as definidas diretamente nos diretórios **android** e **ios**, seja as feitas por pacotes ou SDKs que você instalar, exigirão criar um novo build do seu development build.

Para impor um contrato de API entre as camadas JavaScript e nativa do seu app, defina o valor do [`runtimeVersion`](/eas-update/runtime-versions) na app config. Cada build que você gerar terá esse valor embutido e só carregará bundles com o mesmo `runtimeVersion`, tanto em desenvolvimento quanto em produção.
