Um projeto nativo isolado é complicado de manter, escalar e atualizar. Em um app multiplataforma, você tem vários projetos nativos que precisam ser mantidos e atualizados com as versões mais recentes do sistema operacional para não ficar muito para trás nas dependências de terceiros.

À medida que o seu projeto nativo cresce, a complexidade vinda das dependências de terceiros aumenta, o que dificulta as atualizações e reduz o ritmo do desenvolvedor. Isso desencoraja a adição de funcionalidades nativas avançadas e resulta em apps menos poderosos. Em apps multiplataforma, essa complexidade se multiplica em cada plataforma.

Para resolver isso, apresentamos o conceito de **Geração Nativa Contínua**. Em vez de criar projetos nativos uma única vez e manter as personalizações desses projetos durante toda a vida do código, projetos nativos de vida curta são gerados somente quando necessário, como ao depurar ou fazer o build. Esses projetos são gerados a partir de um template padrão mais a configuração ou o código customizado que define como o template deve ser personalizado. O resultado é um projeto nativo que pode ser compilado em um app nativo com as personalizações desejadas pelo desenvolvedor. No entanto, o desenvolvedor fica responsável apenas por manter a definição das suas personalizações, e não todo o código do projeto nativo.

## CNG em apps React Native \{#cng-in-react-native-apps}

Apps React Native podem usar **CNG** com o [Prebuild](#usage) para automatizar atualizações, instalar ou remover bibliotecas, aplicar personalizações de white label, compartilhar configuração entre vários apps, reduzir o [código órfão](#how-does-prebuild-help-with-orphaned-code) e muito mais.

**O Expo como framework** viabiliza o CNG combinando as seguintes ferramentas:

1. O arquivo de [app config](/workflow/configuration/).
2. Argumentos passados ao comando `npx expo prebuild`.
3. Versão do `expo` instalada no projeto e o [template de prebuild](https://github.com/expo/expo/tree/main/templates/expo-template-bare-minimum) correspondente.
4. [Autolinking](/more/glossary-of-terms#autolinking), para vincular [módulos nativos](/more/glossary-of-terms/#native-module) encontrados no **package.json**.
5. Subscribers nativos, para reduzir os efeitos colaterais do código nativo em arquivos de entrada, como o **MainApplication** ou o **AppDelegate**.
6. Credenciais gerenciadas pelo Expo Build para assinar código de targets e entitlements adicionais.

O resultado final é um workflow em que o dev descreve qualquer app nativo com a app config e gera esse projeto continuamente, rodando `npx expo prebuild`.

## Uso \{#usage}

O Prebuild pode ser usado rodando:

<Terminal
  cmd={{
    npm: ['$ npx expo prebuild'],
    yarn: ['$ yarn expo prebuild'],
    pnpm: ['$ pnpm expo prebuild'],
    bun: ['$ bun expo prebuild'],
  }}
/>

Isso cria os diretórios **android** e **ios** para rodar o seu código React. Se você modificar manualmente os diretórios gerados, corre o risco de perder suas alterações na próxima vez que rodar `npx expo prebuild --clean`. Em vez disso, use [config plugins](/config-plugins/introduction/), que são funções que fazem modificações nos projetos nativos durante o prebuild.

Recomendamos fortemente usar o Prebuild pelos motivos listados na seção [perguntas frequentes](#prebuild), mas o sistema é [totalmente opcional](#optionality), e você pode deixar de usá-lo a qualquer momento.

### Uso com o Expo Build \{#usage-with-expo-build}

Se o seu projeto não tiver os diretórios **android** e **ios**, o Expo Build rodará o Prebuild para gerar esses diretórios nativos antes da compilação. Esse é o comportamento padrão para qualquer projeto criado com `npx create-expo-app`.

Para um projeto que já tem os diretórios **android** e **ios**, o Expo Build não rodará o Prebuild, para não sobrescrever as alterações feitas nos diretórios nativos.

Se você investigar problemas no seu app [compilando-o localmente](/guides/local-app-development/#local-app-compilation) (rodando `npx expo prebuild`, `npx expo run:android` ou `npx expo run:ios`), ainda pode usar o Prebuild com o Expo Build para gerar diretórios nativos novos durante o processo de build. Os diretórios **android** e **ios** são adicionados automaticamente ao **.gitignore** quando você cria um novo projeto, mas, se precisar adicioná-los manualmente, coloque-os no **.gitignore** ou nos arquivos [**.easignore**](/build-reference/easignore/):

<DiffBlock
  raw={`diff --git a/.gitignore b/.gitignore
--- a/.gitignore
+++ b/.gitignore
@@ -0,0 +1,2 @@
+/android
+/ios
`}
/>

### Uso com os comandos run da CLI do Expo \{#usage-with-expo-cli-run-commands}

Você pode fazer um build nativo localmente rodando:

<Terminal
  cmd={{
    npm: [
      '# Build your native Android project',
      '$ npx expo run:android',
      '',
      '# Build your native iOS project',
      '$ npx expo run:ios',
    ],
    yarn: [
      '# Build your native Android project',
      '$ yarn expo run:android',
      '',
      '# Build your native iOS project',
      '$ yarn expo run:ios',
    ],
    pnpm: [
      '# Build your native Android project',
      '$ pnpm expo run:android',
      '',
      '# Build your native iOS project',
      '$ pnpm expo run:ios',
    ],
    bun: [
      '# Build your native Android project',
      '$ bun expo run:android',
      '',
      '# Build your native iOS project',
      '$ bun expo run:ios',
    ],
  }}
/>

Se os diretórios nativos não existirem, `npx expo prebuild` rodará uma vez para a plataforma específica. Nos usos seguintes desses comandos `run`, rode manualmente `npx expo prebuild --clean` para garantir que o código nativo esteja sincronizado do zero com a sua configuração local.

## Suporte a plataformas \{#platform-support}

O Prebuild atualmente oferece suporte a Android e iOS. O suporte à web não é necessário, porque não há projeto nativo a ser gerado para a web, e o app web roda em um navegador. Use a opção `--platform` para rodar o prebuild em plataformas individuais:

<Terminal
  cmd={{
    npm: ['$ npx expo prebuild --platform ios'],
    yarn: ['$ yarn expo prebuild --platform ios'],
    pnpm: ['$ pnpm expo prebuild --platform ios'],
    bun: ['$ bun expo prebuild --platform ios'],
  }}
/>

## Dependências \{#dependencies}

O Prebuild começa inicializando projetos nativos novos a partir de um template correspondente a cada versão do SDK do Expo. Isso também se alinha com versões específicas do React e do React Native. Você verá um aviso ao rodar `npx expo prebuild` quando as versões do React e do React Native do seu projeto forem diferentes das esperadas, especificadas no campo `dependencies` do [**package.json** do template](https://github.com/expo/expo/tree/main/templates/expo-template-bare-minimum).

Você pode evitar a alteração das versões dos pacotes npm com a opção `--skip-dependency-update`:

<Terminal
  cmd={{
    npm: ['$ npx expo prebuild --skip-dependency-update react-native,react'],
    yarn: ['$ yarn expo prebuild --skip-dependency-update react-native,react'],
    pnpm: ['$ pnpm expo prebuild --skip-dependency-update react-native,react'],
    bun: ['$ bun expo prebuild --skip-dependency-update react-native,react'],
  }}
/>

## Gerenciadores de pacotes \{#package-managers}

Quando as [dependências](#dependencies) forem alteradas, o Prebuild reinstalará as bibliotecas usando o gerenciador de pacotes que está em uso no projeto (isso é inferido pelo lockfile). Você pode forçar um gerenciador específico passando uma das opções: `--npm`, `--yarn` ou `--pnpm`.

Todas as instalações podem ser ignoradas passando o comando `--no-install`, o que é útil para testar a geração rapidamente.

## Limpeza \{#clean}

A opção `--clean` apaga os diretórios nativos existentes antes de gerar. Rodar `npx expo prebuild` de novo sem a opção `--clean` vai acrescentar as alterações sobre os arquivos existentes, o que é mais rápido, mas pode não produzir o mesmo resultado em alguns casos.

Por exemplo, alguns config plugins não são idempotentes. Quando um projeto usa vários "dangerous modifiers" para adicionar alterações baseadas em regex ao código do app, isso pode gerar comportamentos inesperados. Por isso, usar a opção `--clean` é a forma mais segura de usar o comando prebuild e é geralmente recomendada na maioria dos casos.

### Usando a opção `--clean` \{#using---clean-option}

Ao usar a opção `--clean`, você receberá um aviso se tiver alterações não commitadas no seu repositório Git, pois essa opção apaga e recria todos os arquivos do seu projeto nativo. Esse aviso é opcional e será ignorado quando encontrado em CI. Você pode desativar essa verificação definindo a variável de ambiente `EXPO_NO_GIT_STATUS=1`.

Há casos em que desenvolvedores querem alternar entre workflows com frequência. Por exemplo, talvez você prefira construir uma funcionalidade personalizada nativamente no Android Studio e no Xcode e, depois, movê-la para config plugins locais.

## Templates \{#templates}

Você pode personalizar a forma como os diretórios nativos são gerados por meio de [config plugins](/config-plugins/introduction). Já existem muitos config plugins para várias modificações, e bibliotecas da comunidade costumam trazer os próprios. Você pode [ver uma lista de alguns plugins populares](https://github.com/expo/config-plugins) para mais informações.

O Prebuild começa a partir de arquivos de template, que depois são modificados com config plugins. Os arquivos de template são baseados na versão do SDK do Expo e vêm do pacote npm [`expo-template-bare-minimum`](https://github.com/expo/expo/tree/main/templates/expo-template-bare-minimum). Você pode trocar o template usado passando `--template /path/to/template.tgz` ao comando `npx expo prebuild`. Isso geralmente não é recomendado, porque os modificadores base em `@expo/prebuild-config` fazem algumas suposições não documentadas sobre os arquivos do template, então pode ser difícil manter um template personalizado.

> **Note:** em ambientes de rede onde todos os pacotes são baixados de um registro privado e o acesso ao registro público do npm está bloqueado, um template disponível localmente precisa ser passado ao comando prebuild. [Saiba mais sobre como usar uma versão local do template padrão](https://expo.fyi/prebuild-without-npm-access).

## Efeitos colaterais \{#side-effects}

O `npx expo prebuild` executa vários efeitos colaterais além de gerar os diretórios **android** e **ios**. Há trabalho em andamento para eliminar esses efeitos colaterais: o ideal é que rodar `npx expo prebuild` gere os projetos Android e iOS e deixe o restante do projeto intacto.

Além de gerar os diretórios nativos, o prebuild também faz as seguintes modificações:

- Altera o campo `scripts` no **package.json** para trocar `expo start --android` e `expo start --ios` por `expo run:android` e `expo run:ios`
- Altera o campo `dependencies` no **package.json**

A alteração de conveniência no campo `scripts` é o único efeito colateral que muda a forma como você trabalha no seu app antes e depois do prebuild. Todas as outras alterações podem ser mantidas e commitadas no Git para minimizar o diff ao rodar o prebuild.

## Opcionalidade \{#optionality}

O Prebuild é opcional e funciona perfeitamente com todas as ferramentas e serviços do Expo. Para [projetos React Native existentes](/bare/overview/), em que os projetos nativos são gerenciados manualmente, não use `npx expo prebuild`, pois isso pode sobrescrever as personalizações manuais. Os desenvolvedores podem continuar fazendo ([alterações diretas nos seus projetos nativos](/more/glossary-of-terms/#bare-workflow)) enquanto adotam outras ferramentas e workflows do Expo. Mais tarde, eles podem mover suas personalizações manuais para a app config e/ou config plugins, e então adotar o CNG.

Tudo o que o Expo oferece, incluindo os [Serviços do Expo](/eas/), a CLI do Expo e as bibliotecas do SDK do Expo, foi criado para dar **suporte total** a projetos React Native existentes, já que isso é um requisito mínimo para oferecer suporte a projetos que usam `npx expo prebuild`. A única exceção é o app [Expo Go](https://expo.dev/go), que só pode carregar projetos React Native arbitrários se eles incluírem fallbacks em JavaScript para código nativo ausente no runtime do Expo Go.

## Perguntas frequentes \{#common-questions}

<FAQ>

### CNG \{#cng}

<Collapsible summary="Como o CNG ajuda nas atualizações do projeto?">

Desenvolvedores de React Native que não usam a **Geração Nativa Contínua** relataram que atualizar os seus apps para a versão mais recente do React Native é o principal ponto fraco da biblioteca, segundo a [React Native Survey (2022)](https://results.2022.stateofreactnative.com/opinions/#opinions_pain_points).

Ao usar o CNG, o processo de atualização consiste simplesmente em atualizar as dependências npm e a app config, e rodar novamente `npx expo prebuild --clean`.

</Collapsible>

<Collapsible summary="Como um autor de biblioteca React Native pode adotar o CNG?">

Autores de bibliotecas React Native podem adotar o CNG de várias formas. Depende da complexidade das bibliotecas. Veja alguns cenários:

- **Sem código nativo ou efeitos colaterais de configuração**: bibliotecas sem código nativo ou efeitos colaterais de configuração, como o `react-native-blurhash`, podem se integrar perfeitamente ao `npx expo prebuild`. Elas podem depender da Resolução de Módulos do Node sem precisar de nenhuma configuração adicional.

- **Código nativo sem configuração extra depois da instalação**: bibliotecas com código nativo costumam ser instaladas e vinculadas automaticamente pelo [Autolinking do Expo](/more/glossary-of-terms#autolinking), que roda antes de o app nativo ser compilado.

- **Efeitos colaterais de configuração e configuração adicional**: bibliotecas que exigem efeitos colaterais de configuração podem adotar o CNG criando [config plugins do Expo](/config-plugins/introduction/) para as suas bibliotecas. Essa abordagem permite que os autores automatizem a adição de valores como mensagens de permissão no **Info.plist** ou a injeção de targets no projeto do Xcode.

- **Bibliotecas que dependem de hooks nativos de runtime**: bibliotecas que dependem de hooks específicos de runtime nativo, como interceptar a URL de inicialização via `AppDelegate`, `MainActivity`, `MainApplication` e assim por diante, podem usar os [**Lifecycle listeners**](/modules/android-lifecycle-listeners/) da API de Módulos do Expo. Esses listeners permitem aplicar esses hooks de runtime pelo Autolinking do Expo, em vez de modificar esses arquivos padrão do projeto nativo, eliminando a necessidade de um config plugin.

Muitas bibliotecas e serviços complexos já oferecem suporte ao CNG pelo Expo Prebuild, como [MapBox](https://github.com/rnmapbox/maps), [Sentry](https://github.com/getsentry/sentry-react-native), [Stripe](https://github.com/stripe/stripe-react-native) e [React Native Firebase](https://rnfirebase.io/#installation-for-expo-projects).

Adotar o CNG pelos autores de bibliotecas não é um pré-requisito para usar `npx expo prebuild`. Se um autor de biblioteca ainda não adotou o CNG, os desenvolvedores ainda podem usar `npx expo prebuild` criando [Config Plugins](https://github.com/expo/config-plugins/) locais para modificar o pipeline de geração nativa. Essa flexibilidade torna o CNG acessível e benéfico para todos os desenvolvedores da comunidade React Native.

</Collapsible>

<Collapsible summary="O CNG se limita a projetos React Native?">

Não, o CNG é um padrão versátil que pode ser aplicado a qualquer projeto nativo. Embora o Expo Prebuild seja uma ferramenta que implementa o CNG especificamente para projetos React Native, o conceito em si não se limita a esse framework.

</Collapsible>

<Collapsible summary="Como a comunidade usa o CNG?">

Veja alguns exemplos da comunidade de funcionalidades nativas difíceis convertidas em arquivos de configuração simples, que permitiram aos desenvolvedores criar apps mais poderosos sem abrir mão da velocidade de iteração:

- [Extensões do Safari para iOS](https://github.com/andrew-levy/react-native-safari-extension): aqui, o processo de criar uma extensão do Safari para iOS, notoriamente difícil de implementar, é reduzido a algumas linhas de JSON.

- [App de figurinhas para o iMessage](https://github.com/expo/config-plugins/tree/main/packages/ios-stickers): este config plugin do Expo pode gerar um app inteiro de figurinhas para o iMessage a partir de um objeto JSON.

- [Toda a suíte do Firebase](https://rnfirebase.io/): aqui você pode ver toda a suíte nativa do Firebase, que passa de um processo de configuração nativa em várias etapas, em várias IDEs, para uma configuração JSON básica.

- [Widgets de tela inicial multiplataforma](https://github.com/gaishimo/eas-widget-example): este config plugin do Expo pode gerar um widget de tela inicial para Android e iOS.

- [Apple App Clips](https://github.com/bndkt/react-native-app-clip): este config plugin do Expo transforma o processo de gerar um Apple App Clip, que é um processo em várias etapas e em vários targets, em uma única linha: `["react-native-app-clip", { "name": "My App Clip" }]`.

A qualquer momento, esses recursos podem ser facilmente adicionados e removidos, sem efeitos colaterais. O CNG permite que os desenvolvedores experimentem recursos complexos e os iterem rapidamente, sem se preocupar com custos de manutenção de longo prazo ou com código órfão potencial no projeto.

</Collapsible>

<Collapsible summary="O CNG pode ser usado para sistemas operacionais além de Android e iOS?">

Claro! O CNG é um conceito abstrato que pode ser aplicado a qualquer sistema operacional. Embora o Expo Prebuild implemente oficialmente o CNG para Android e iOS, ele também oferece suporte abstrato a plataformas para que os desenvolvedores criem implementações para plataformas adicionais.

</Collapsible>

<Collapsible summary="Usar o Expo é um requisito para o CNG?">

De forma alguma. O CNG é um padrão aberto que pode ser adotado por qualquer comunidade. Definimos o padrão de forma abstrata para ajudar outras comunidades a entender como adotar o CNG nos próprios projetos.

</Collapsible>

<Collapsible summary="Como o CNG se compara a padrões de desenvolvimento web como a Geração de Sites Estáticos (SSG)?">

O CNG tem semelhanças com o SSG, pois ambos geram um projeto a partir de um conjunto de entradas. No entanto, o CNG difere do SSG na saída. Ele gera código de runtime nativo em vez de código de site estático. Isso significa que o projeto nativo é gerado sob demanda, e o código-fonte e a configuração gerados são descartados assim que o projeto nativo é compilado em um app nativo.

</Collapsible>

<Collapsible summary="É possível usar o CNG com um projeto brownfield existente?">

O CNG foi projetado para gerenciar continuamente todo o estado de um projeto nativo. Por isso, ele não é destinado a projetos brownfield existentes. No entanto, você pode usar o CNG para gerar um novo projeto nativo, que depois pode ser integrado a um projeto brownfield existente.

</Collapsible>

### Prebuild \{#prebuild}

O Expo Prebuild agiliza o processamento do CNG. Estes são alguns problemas do ciclo de desenvolvimento React Native que o Prebuild resolve:

<Collapsible summary="Como o Prebuild pode ajudar nas atualizações do projeto?">

Construir código nativo exige familiaridade com as ferramentas da plataforma, o que cria uma curva de aprendizado acentuada. Esse desafio se intensifica no desenvolvimento multiplataforma, por causa de várias plataformas. Ferramentas multiplataforma não ajudam se você precisar implementar muitos recursos em código nativo específico de cada plataforma.

Ao criar a estrutura de um app nativo, existe um código e uma configuração iniciais que você talvez não entenda. Mesmo assim, você não é responsável por mantê-los. Com o tempo, você vai precisar entender esse código para atualizar o seu app com segurança. Esse desafio costuma levar os desenvolvedores a atualizar de forma incorreta ou a criar um app novo, copiando o código-fonte existente.

**Com o Prebuild**, atualizar fica muito mais parecido com atualizar um app JavaScript puro. Aumente as versões no seu **package.json**, gere o projeto nativo de novo, e você deve estar pronto para continuar o desenvolvimento.

</Collapsible>

<Collapsible summary="Como o Prebuild simplifica a configuração multiplataforma?">

Configurações multiplataforma, como ícone do app, nome, splash screen e assim por diante, precisam ser implementadas manualmente em código nativo. Essas implementações costumam ser bem diferentes em cada plataforma.

**Com o Prebuild**, as configurações multiplataforma são tratadas no nível do config plugin, e o desenvolvedor só precisa definir um único valor, como `"icon": "./icon.png"`, para que toda a geração de ícones seja feita automaticamente.

</Collapsible>

<Collapsible summary="Como posso gerenciar os efeitos colaterais de dependências com o Prebuild?">

Muitos pacotes nativos complexos exigem configuração adicional além da instalação e do [autolinking](/more/glossary-of-terms#autolinking). Por exemplo, uma biblioteca de câmera exige que as configurações de permissão sejam adicionadas ao **AndroidManifest.xml** no Android e ao **Info.plist** no iOS. Essa configuração adicional pode ser considerada um efeito colateral de configuração do pacote. Colar o código desse efeito colateral nos arquivos nativos do seu projeto pode gerar erros de compilação nativa difíceis, e é um código pelo qual você passa a ser responsável e que precisa manter.

**Com o Prebuild**, os autores de bibliotecas, que conhecem a configuração da sua biblioteca melhor do que ninguém, podem criar um script testável e versionado chamado [config plugin](/config-plugins/introduction/) para automatizar a adição dos efeitos colaterais de configuração exigidos pela biblioteca. Isso significa que os efeitos colaterais da biblioteca podem ser mais expressivos, poderosos e estáveis. Para efeitos colaterais de código nativo, também oferecemos [Android Lifecycle Listeners](/modules/android-lifecycle-listeners) e [AppDelegate Subscribers](/modules/appdelegate-subscribers), que vêm por padrão no [template de prebuild](#templates).

</Collapsible>

<Collapsible summary="Como o Prebuild ajuda com código órfão?">

Quando você desinstala um pacote, precisa ter certeza de que removeu todos os efeitos colaterais necessários para que ele funcionasse. Se você deixar algo para trás, surge um código órfão que não pode ser associado a nenhum pacote específico. Esse código se acumula e torna o projeto mais difícil de entender e manter.

**Com o Prebuild**, o único efeito colateral é o [config plugin](/config-plugins/introduction/) na config do Expo do projeto (**app.json**), que gera um erro quando o módulo do Node correspondente é desinstalado. Assim, sobra muito menos configuração órfã.

</Collapsible>

<Collapsible summary="Quando o Prebuild pode não ser a escolha certa para um projeto">

Estes são alguns motivos pelos quais o Expo Prebuild pode **não** ser a escolha certa para um projeto específico:

#### Compatibilidade de plataforma \{#platform-compatibility}

O Prebuild só pode ser usado para plataformas nativas compatíveis com o SDK do Expo. Por enquanto, isso significa Android e iOS. A exceção é a web, que não precisa do `npx expo prebuild`, pois usa o navegador em vez de um runtime nativo personalizado.

#### Fazer alterações diretamente é mais rápido do que modularizar e automatizar \{#making-changes-directly-is-quicker-than-modularizing-and-automating}

Todas as alterações nativas precisam ser adicionadas com módulos nativos (usando as APIs de Módulos Nativos integradas do React Native ou a API de Módulos do Expo) e config plugins. Isso significa que, se você quiser adicionar rapidamente um arquivo nativo ao projeto para experimentar, talvez seja melhor rodar o prebuild, adicionar o arquivo manualmente e depois voltar ao sistema com um [monorepo](/guides/monorepos). Planejamos acelerar esse processo adicionando funcionalidades ao [Autolinking do Expo](/more/glossary-of-terms#expo-autolinking) que encontram arquivos de projeto nativo fora dos diretórios nativos e os vinculam antes do build.

Se você quiser modificar a configuração, como o arquivo **gradle.properties**, precisará escrever um plugin ([exemplo](https://github.com/expo/expo/blob/1c994bb042ad47fbf6878e3b5793d4545f2d1208/apps/native-component-list/app.config.js#L21-L28)). Isso pode ser facilmente automatizado com bibliotecas auxiliares de plugins, mas fica um pouco mais lento se você precisar fazer isso com frequência.

#### Suporte a config plugins na comunidade \{#config-plugin-support-in-the-community}

Nem todos os pacotes oferecem suporte ao _Expo Prebuild_ ainda. Se você encontrar uma biblioteca que exige configuração extra após a instalação e ainda não tem um config plugin, recomendamos abrir um pull request ou uma issue para que o mantenedor fique ciente da solicitação de funcionalidade.

Muitos pacotes, como o [`react-native-blurhash`](https://github.com/mrousavy/react-native-blurhash), não exigem nenhuma configuração nativa adicional além do que é resolvido pelo [autolinking](/more/glossary-of-terms#autolinking), então nenhum config plugin é necessário.

Outros pacotes, como o [`react-native-ble-plx`](https://github.com/Polidea/react-native-ble-plx), exigem configuração adicional e, por isso, precisam de um config plugin para serem usados com `npx expo prebuild` (nesse caso, existe um plugin externo chamado [`@config-plugins/react-native-ble-plx`](https://github.com/expo/config-plugins/tree/main/packages/react-native-ble-plx)).

Como alternativa, também temos um repositório de [config plugins fora da árvore](https://github.com/expo/config-plugins), que oferece plugins para pacotes populares que ainda não adotaram o sistema. Pense nele como o [DefinitelyTyped](https://github.com/DefinitelyTyped/DefinitelyTyped) para TypeScript. Preferimos que os pacotes tragam o próprio config plugin, mas, se ainda não tiverem adotado o sistema, a comunidade pode usar os pacotes listados no repositório.
