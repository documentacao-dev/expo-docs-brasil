A app config (**app.json**, **app.config.js**, **app.config.ts**) é usada para configurar a geração do [Expo Prebuild](/more/glossary-of-terms/#prebuild), como um projeto é carregado no [Expo Go](/get-started/set-up-your-environment/) e o manifesto de atualizações OTA.

Ela precisa ficar na raiz do projeto, ao lado do **package.json**. Veja um exemplo mínimo:

```json app.json
{
  "name": "My app",
  "slug": "my-app"
}
```

Se a sua config do Expo tiver um objeto `expo: {}` no nível superior, ele será usado no lugar do objeto raiz e todas as outras chaves serão ignoradas.

## Propriedades \{#properties}

A app config define várias coisas, como nome do app, ícone, splash screen, esquema de deep linking, chaves de API usadas por alguns serviços e assim por diante. Para a lista completa de propriedades disponíveis, consulte a [referência de app.json/app.config.js/app.config.ts](/versions/latest/config/app/).

> **info** Você usa o Visual Studio Code? Se sim, recomendamos instalar a extensão [Expo Tools](https://marketplace.visualstudio.com/items?itemName=expo.vscode-expo-tools) para ter preenchimento automático das propriedades nos arquivos **app.json**.

## Lendo valores de configuração no seu app \{#reading-configuration-values-in-your-app}

A maior parte da configuração da app config pode ser acessada em tempo de execução pelo seu código JavaScript, usando [`Constants.expoConfig`](/versions/latest/sdk/constants/#nativeconstants). Você **não deve** incluir nenhuma informação sensível na app config (com algumas exceções para os campos que são filtrados, como detalhado abaixo).

Você pode verificar quais configurações serão incorporadas aos seus builds e atualizações e ficarão disponíveis em tempo de execução rodando `npx expo config --type public`.

<Collapsible summary="Quais campos são filtrados da app config pública?">

Os campos a seguir são filtrados da app config pública (e não ficam acessíveis pelo objeto `Constants.expoConfig`):

- [`ios.config`](/versions/latest/config/app/#config)
- [`android.config`](/versions/latest/config/app/#config-1)
- [`updates.codeSigningCertificate`](/versions/latest/config/app/#codesigningcertificate)
- [`updates.codeSigningMetadata`](/versions/latest/config/app/#codesigningmetadata)

> **warning** Também evite importar o **app.json** ou o **app.config.js** diretamente no seu código JavaScript, porque isso importa o arquivo inteiro e não uma versão processada dele. Em vez disso, use [`Constants.expoConfig`](/versions/latest/sdk/constants/#nativeconstants) para acessar a configuração.

## Estendendo a configuração \{#extending-configuration}

Autores de bibliotecas podem estender a app config usando [config plugins do Expo](/config-plugins/introduction/).

> **info** Os config plugins são usados principalmente para configurar o comando [`npx expo prebuild`](/more/glossary-of-terms/#prebuild).

## Configuração dinâmica \{#dynamic-configuration}

Para mais personalização, você pode usar JavaScript (**app.config.js**) ou [TypeScript](#using-typescript-for-configuration-appconfigts-instead-of-appconfigjs) (**app.config.ts**). Essas configs têm as seguintes propriedades:

- Comentários, variáveis e aspas simples.
- Sintaxe `import` do ESM tanto em **app.config.js** quanto em **app.config.ts**, incluindo a importação de outros arquivos JavaScript.
- Suporte a TypeScript (**app.config.ts**) com coalescência nula e encadeamento opcional. Importar outros arquivos TypeScript ou personalizar recursos da linguagem exige [`tsx`](/guides/typescript/#app-config).
- Atualizada sempre que o Metro bundler recarrega.
- Fornece informações do ambiente para o seu app.
- Não oferece suporte a Promises.

> **info** **Observação**: os arquivos **app.config.mts**, **app.config.cts**, **app.config.mjs** e **app.config.cjs** também são encontrados. Por padrão, a config é transpilada para CommonJS, e os arquivos `.js` e `.ts` podem misturar sintaxe ESM e CommonJS. Quando essa mistura causar problemas de import ou require, use uma das extensões explícitas para fixar a config em um único formato de módulo.

Por exemplo, você pode exportar um objeto para definir sua config personalizada:

```js app.config.js
const myValue = 'My App';

module.exports = {
  name: myValue,
  version: process.env.MY_CUSTOM_PROJECT_VERSION || '1.0.0',
  // All values in extra will be passed to your app.
  extra: {
    fact: 'kittens are cool',
  },
};
```

A chave `"extra"` permite passar dados de configuração arbitrários para o seu app. O valor dessa chave é acessado usando [`expo-constants`](/versions/latest/sdk/constants/):

```js App.js
import Constants from 'expo-constants';

Constants.expoConfig.extra.fact === 'kittens are cool';
```

Você pode acessar e modificar os valores de configuração recebidos exportando uma função que retorna um objeto. Isso é útil se o seu projeto também tiver um **app.json**. Por padrão, a CLI do Expo lê primeiro o **app.json** e envia o resultado normalizado para o **app.config.js**.

Por exemplo, o seu **app.json** pode ficar assim:

```json app.json
{
  "name": "My App"
}
```

E no seu **app.config.js** você recebe essa configuração nos argumentos da função exportada:

```js app.config.js
module.exports = ({ config }) => {
  console.log(config.name); // prints 'My App'
  return {
    ...config,
  };
};
```

### Alternando a configuração de acordo com o ambiente \{#switching-configuration-based-on-the-environment}

É comum ter configurações diferentes em desenvolvimento, staging e produção, ou trocar a configuração inteira para fazer white label de um app. Para isso, você pode usar o **app.config.js** junto com variáveis de ambiente.

```js app.config.js
module.exports = () => {
  if (process.env.MY_ENVIRONMENT === 'production') {
    return {
      /* your production config */
    };
  } else {
    return {
      /* your development config */
    };
  }
};
```

Para usar essa configuração com os comandos da CLI do Expo, defina a variável de ambiente para comandos específicos ou no seu perfil do shell. Para definir variáveis de ambiente em um comando específico, coloque as variáveis e os valores antes do comando, como mostrado no exemplo:

<Terminal cmd={['$ MY_ENVIRONMENT=production eas update']} />

Isso não é exclusivo da CLI do Expo. No Windows, você pode aproximar o comando acima assim:

<Terminal
  cmd={{
    npm: ['$ npx cross-env MY_ENVIRONMENT=production eas update'],
    yarn: ['$ yarn dlx cross-env MY_ENVIRONMENT=production eas update'],
    pnpm: ['$ pnpm dlx cross-env MY_ENVIRONMENT=production eas update'],
    bun: ['$ bunx cross-env MY_ENVIRONMENT=production eas update'],
  }}
/>

Ou você pode usar qualquer outro mecanismo com o qual se sinta à vontade para variáveis de ambiente.

### Usando TypeScript na configuração: app.config.ts em vez de app.config.js \{#using-typescript-for-configuration-appconfigts-instead-of-appconfigjs}

Você pode ter autocompletar e blocos de documentação em uma config do Expo em TypeScript. Crie um **app.config.ts** com o seguinte conteúdo:

```ts app.config.ts
import { ExpoConfig, ConfigContext } from 'expo/config';

export default ({ config }: ConfigContext): ExpoConfig => ({
  ...config,
  slug: 'my-app',
  name: 'My App',
});
```

Para importar outros arquivos TypeScript no **app.config.ts** ou personalizar os recursos da linguagem, recomendamos usar o [`tsx`](/guides/typescript/#app-config). O `tsx` também permite usar a sintaxe `import` em qualquer arquivo importado pelo **app.config.ts**. Isso significa que você pode escrever [config plugins](/config-plugins/introduction/) locais em TypeScript com todos os recursos da linguagem.

### Regras de resolução da configuração \{#configuration-resolution-rules}

Existem dois tipos de config: estática (**app.config.json**, **app.json**) e dinâmica (**app.config.js**, **app.config.ts**). As configs estáticas podem ser atualizadas automaticamente pelas ferramentas de linha de comando, enquanto as dinâmicas precisam ser atualizadas manualmente pelo desenvolvedor.

1. A config estática é lida se o **app.config.json** existir (com fallback para o **app.json**). Se nenhuma config estática existir, os valores padrão são inferidos a partir do **package.json** e das suas dependências.
2. A config dinâmica é lida se existir o **app.config.ts** ou o **app.config.js**. Se os dois existirem, a config TypeScript é usada.
3. Se a config dinâmica retornar uma função, a config estática é passada para a função com `({ config }) => ({})`. Essa função pode então alterar os valores da config estática. Pense nisso como um middleware para a config estática.
4. O valor retornado pela config dinâmica é usado como config final. Ele não pode conter Promises.
5. Todas as funções da config são avaliadas e serializadas antes que qualquer ferramenta do ecossistema Expo as use. A config precisa ser um manifesto JSON quando for hospedada.
6. Se o objeto final de config tiver um objeto `expo: {}` no nível superior, ele será usado no lugar do objeto raiz e todas as outras chaves serão ignoradas.

Rodar `npx expo config` exibe a configuração final que será usada pela CLI do Expo depois que a resolução ocorrer.
