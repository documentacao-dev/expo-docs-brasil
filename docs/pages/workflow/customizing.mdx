- [Usando bibliotecas que incluem código nativo](#using-libraries-that-include-native-code)
- [Escrevendo código nativo](#writing-native-code)

## Usando bibliotecas que incluem código nativo \{#using-libraries-that-include-native-code}

Desenvolvedores de Expo e React Native passam a maior parte do tempo escrevendo código JavaScript e usando APIs e componentes nativos disponibilizados por bibliotecas como [`expo-camera`](/versions/latest/sdk/camera/), [`react-native-safe-area-context`](/versions/latest/sdk/safe-area-context/) e o próprio `react-native`. Essas bibliotecas permitem que os desenvolvedores acessem e usem recursos do dispositivo a partir do código JavaScript. Elas também podem dar acesso a um SDK de serviço de terceiros implementado em código nativo (como o [`@sentry/react-native`](/guides/using-sentry/), que oferece bindings para o SDK nativo do Sentry no Android e no iOS).

<Collapsible summary="Usando o Expo Go?">

Se você estiver usando o [Expo Go](https://expo.dev/go), [só pode acessar bibliotecas nativas incluídas no SDK do Expo](/versions/latest/sdk/third-party-overview/) ou bibliotecas que não incluam nenhum código nativo personalizado ([saiba mais sobre bibliotecas de terceiros](/workflow/using-libraries/#third-party-libraries)). [Criar um development build](/develop/development-builds/introduction/) permite alterar o código nativo ou a configuração como em qualquer outro app nativo.

</Collapsible>

### Instalando bibliotecas com código nativo personalizado em development builds \{#installing-libraries-with-custom-native-code-in-development-builds}

Ao usar [development builds](/develop/development-builds/introduction/), trabalhar com bibliotecas que têm código nativo personalizado é simples:

- Instale a biblioteca com o npm, por exemplo: `npx expo install react-native-localize`
- Se a biblioteca incluir um [config plugin](/config-plugins/introduction/), você pode especificar a configuração desejada na app config.
- Crie um novo development build ([localmente](/guides/local-app-development/) ou com o [Expo Build](/develop/development-builds/introduction/?buildenv=build-with-expo-services#how-would-you-like-to-build-your-development-build)).

Agora você pode usar a biblioteca no código do seu app.

<Collapsible summary="Conceitos-chave e fluxo de desenvolvimento">

A [visão geral do desenvolvimento](/workflow/overview/) traz detalhes sobre os conceitos-chave para desenvolver um app com o Expo e o fluxo do ciclo principal de desenvolvimento.

</Collapsible>

## Escrevendo código nativo \{#writing-native-code}

Use a [API de Módulos do Expo](/modules/overview/) para escrever código em Swift e Kotlin e adicionar novos recursos ao seu app com módulos e views nativos. Existem outras ferramentas que você pode usar para criar módulos nativos, mas acreditamos que usar a API de Módulos do Expo torna a criação e a manutenção de quase todos os tipos de módulos do React Native o mais simples possível. Achamos que a API de Módulos do Expo é a melhor escolha para a maioria dos desenvolvedores que criam módulos nativos para os seus apps.

<Collapsible summary="Quando devo considerar escrever código nativo?">

É comum encontrar situações em que uma biblioteca não faz exatamente o que você precisa. Por exemplo, a biblioteca pode não dar acesso a um recurso específico da plataforma, ou um serviço de terceiros pode não oferecer bindings para o React Native.

</Collapsible>

<Collapsible summary="Você está pensando em escrever um módulo principalmente em C++?">

Se você pretende escrever um módulo nativo principalmente em C++, talvez queira explorar a [API de Turbo Modules](https://github.com/reactwg/react-native-new-architecture/blob/main/docs/turbo-modules.md) fornecida pelo React Native.

</Collapsible>

### Criando um módulo local \{#creating-a-local-module}

Se você pretende usar o seu módulo nativo em um único app (você sempre pode mudar de ideia depois), recomendamos [usar um "módulo local" do Expo](/modules/get-started/#create-the-local-expo-module) para escrever código nativo personalizado. Os módulos locais do Expo funcionam de forma parecida com os [Módulos do Expo](/modules/overview) usados por desenvolvedores de bibliotecas e dentro do SDK do Expo, como o `expo-camera`, mas não são publicados no npm. Em vez disso, você os cria diretamente dentro do seu projeto.

Criar um módulo local gera a estrutura de um módulo em Swift e Kotlin dentro do diretório `modules` do seu projeto, e esses módulos são vinculados automaticamente ao seu app.

<Terminal
  cmd={{
    npm: ['$ npx create-expo-module@latest --local', '$ npx expo run'],
    yarn: ['$ yarn create expo-module --local', '$ yarn expo run'],
    pnpm: ['$ pnpm create expo-module --local', '$ pnpm expo run'],
    bun: ['$ bun create expo-module --local', '$ bun expo run'],
  }}
/>

### Compartilhando um módulo com vários apps \{#sharing-a-module-with-multiple-apps}

Se você pretende usar o seu módulo nativo em vários apps, use `npx create-expo-module@latest`, sem a flag `--local`, e [crie um módulo independente](/modules/use-standalone-expo-module-in-your-project/). Você pode publicar o seu pacote no npm ou colocá-lo em um diretório de pacotes do seu [monorepo](/guides/monorepos/) (se tiver um) para usá-lo de forma [parecida com os módulos locais](/modules/use-standalone-expo-module-in-your-project/).

## Considerações ao usar a Geração Nativa Contínua (CNG) \{#considerations-when-using-continuous-native-generation-cng}

As sugestões a seguir são mais importantes ao usar o [CNG](/workflow/continuous-native-generation/), mas são boas diretrizes mesmo que você não o utilize.

<Collapsible summary="Faça o build localmente para a melhor experiência de depuração e feedback rápido">

Por padrão, projetos Expo criados com `create-expo-app` usam CNG e não contêm os diretórios nativos **android** ou **ios** até que você rode o comando `npx expo prebuild` no projeto. Ao usar CNG, os desenvolvedores normalmente não commitam os diretórios **android** e **ios** no controle de versão e não os geram localmente, já que o Expo Build faz isso automaticamente durante o processo de build. Dito isso, é comum gerar os diretórios nativos e fazer o build localmente com `npx expo run` ao escrever código nativo personalizado, para ter um ciclo de feedback rápido e acesso completo às ferramentas de depuração nativa no Android Studio e no Xcode.

</Collapsible>

<Collapsible summary="Use config plugins para a configuração do projeto nativo">

Se o seu código nativo exigir alterações na configuração do projeto, como modificar o **AndroidManifest.xml** ou o **Info.plist** do projeto, [aplique essas alterações por meio de um config plugin](/modules/config-plugin-and-native-module-tutorial/) em vez de modificar os arquivos diretamente nos diretórios **android** e **ios**. Lembre-se de que alterações feitas diretamente nos diretórios do projeto nativo serão perdidas na próxima vez que você rodar o prebuild com CNG.

</Collapsible>

<Collapsible summary="Use subscribers de eventos para se conectar aos eventos do ciclo de vida do app">

Se precisar se conectar aos eventos do ciclo de vida do Android ou aos métodos do `AppDelegate`, use as APIs fornecidas pelos Módulos do Expo para [Android](/modules/android-lifecycle-listeners/) e [iOS](/modules/appdelegate-subscribers/) para isso, em vez de modificar diretamente os arquivos-fonte nos diretórios do seu projeto nativo ou de usar um config plugin para adicionar o código, o que não funciona bem com outros plugins.

</Collapsible>
