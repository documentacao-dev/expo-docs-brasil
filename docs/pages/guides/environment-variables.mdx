Variáveis de ambiente são pares de chave e valor configurados fora do seu código-fonte que permitem que o app se comporte de maneira diferente de acordo com o ambiente. Por exemplo, você pode ativar ou desativar determinados recursos ao gerar uma versão de teste do app, ou trocar para um endpoint de API diferente ao gerar a versão de produção.

O Expo CLI carrega automaticamente as variáveis de ambiente com o prefixo `EXPO_PUBLIC_` a partir de arquivos **.env** para uso no seu código JavaScript sempre que você usa o Expo CLI, como ao executar `npx expo start` para iniciar o app no modo de desenvolvimento local.

## Lendo variáveis de ambiente de arquivos .env \{#reading-environment-variables-from-env-files}

Crie um arquivo **.env** na raiz do diretório do projeto e adicione as variáveis específicas de cada ambiente, uma por linha, no formato `EXPO_PUBLIC_[NAME]=VALUE`:

```bash .env
EXPO_PUBLIC_API_URL=https://staging.example.com
EXPO_PUBLIC_API_KEY=abc123
```

Agora você pode usar as variáveis de ambiente diretamente no seu código-fonte:

```tsx
import { Button } from 'react-native';

function Post() {
  const apiUrl = process.env.EXPO_PUBLIC_API_URL;

  async function onPress() {
    await fetch(apiUrl, { ... })
  }

  return <Button onPress={onPress} title="Post" />;
}
```

Quando você executa `npx expo start`, `process.env.EXPO_PUBLIC_API_URL` é substituído por `https://staging.example.com` no bundle do app. As variáveis podem ser atualizadas enquanto você edita o código, sem reiniciar o Expo CLI nem limpar o cache. Você precisará fazer um recarregamento completo (por exemplo, sacudir o dispositivo e depois selecionar Reload no Expo Go ou no seu development build) para ver o valor atualizado.

> **warning** Não armazene informações sensíveis, como chaves privadas, em variáveis `EXPO_PUBLIC_`. Essas variáveis ficam visíveis em texto puro no seu app compilado.

### Como as variáveis são carregadas \{#how-variables-are-loaded}

O Expo CLI carrega os arquivos **.env** de acordo com a [resolução padrão de arquivos **.env**](#using-multiple-env-files-to-define-separate-environments) e, em seguida, substitui todas as referências no seu código a `process.env.EXPO_PUBLIC_[VARNAME]` pelo valor correspondente definido nos arquivos **.env**. O código dentro de **node_modules** não é afetado, por motivos de segurança.

### Como ler variáveis de ambiente \{#how-to-read-from-environment-variables}

- <YesIcon small /> **Cada variável de ambiente deve ser referenciada estaticamente como uma propriedade de
  `process.env`, usando a notação de ponto do JavaScript, para ser incorporada ao código.** Por exemplo,
  a expressão `process.env.EXPO_PUBLIC_KEY` é válida e será incorporada.

- <NoIcon small /> **Versões alternativas da expressão não são compatíveis**. Por exemplo,
  `process.env['EXPO_PUBLIC_KEY']` ou `const {EXPO_PUBLIC_X} = process.env` são inválidas e não serão
  incorporadas.

### Usando vários arquivos .env para definir ambientes separados \{#using-multiple-env-files-to-define-separate-environments}

Cada comando do Expo é executado no modo de desenvolvimento ou de produção. O modo determina quais arquivos **.env** são carregados, e os arquivos listados primeiro têm prioridade:

| Modo        | Arquivos                                                                   |
| ----------- | -------------------------------------------------------------------------- |
| Development | **.env.development.local**, **.env.local**, **.env.development**, **.env** |
| Production  | **.env.production.local**, **.env.local**, **.env.production**, **.env**   |

No SDK 58 e versões posteriores, os comandos do Expo não carregam outros arquivos **.env**, como **.env.staging** ou **.env.test**.

Você pode fazer commit do arquivo **.env** padrão ou de outras configurações padrão, mas os arquivos **.env.local** geralmente devem ser adicionados ao seu **.gitignore**, porque são usados para definir configurações de ambiente específicas da sua máquina local (como o endereço IP da sua rede, caso precise dele para fazer uma requisição a um servidor local).

```bash .gitignore
.env*.local
```

#### Variáveis de ambiente e `NODE_ENV` \{#environment-variables-and-node_env}

`NODE_ENV` é a variável padrão do Node.js que identifica em qual modo o código está sendo executado (normalmente `development`, `production` ou `test`). Ferramentas como resolvedores de módulos, bundlers e executores de testes leem essa variável para decidir como compilar, instalar ou executar o código.

No SDK 58 e versões posteriores, cada comando define `NODE_ENV` com o seu modo e substitui qualquer valor que você tenha definido. Por exemplo, `NODE_ENV=production npx expo start` é executado no modo de desenvolvimento e carrega **.env.development**.

| Comando                                                   | Modo                                                                                      |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `npx expo start`                                          | Desenvolvimento. Produção com `--no-dev`.                                                 |
| `npx expo export`                                         | Produção. Desenvolvimento com `--dev`.                                                    |
| `npx expo run:android`                                    | Desenvolvimento para as variantes `debug` e `debugOptimized`. Produção nos demais casos.  |
| `npx expo run:ios`                                        | Desenvolvimento para configurações com `Debug` no nome. Produção nos demais casos.        |
| `npx expo config`, `npx expo prebuild`, `npx expo-doctor` | Desenvolvimento. Produção no Expo Build.                                                  |

Configurações personalizadas, variantes e flavors continuam funcionando e seguem as mesmas regras.

Outras ferramentas que se baseiam nos comandos do Expo CLI apresentam o mesmo comportamento. Por exemplo, `eas update` chama `npx expo export` e, por isso, `NODE_ENV=test eas update` também não será executado com `NODE_ENV` definido como `test` (ele será `production`). A variável `NODE_ENV` é usada por muitas ferramentas de formas diferentes (por exemplo, se você executar `NODE_ENV=production npm install`, as suas `devDependencies` não serão instaladas). Por isso, em projetos React Native, é melhor não sobrecarregá-la para alternar entre arquivos **.env**.

Se você usa o Expo Services, considere usar `eas env:pull`. Esse comando troca o seu **.env.local** por um ambiente de sua escolha, em vez de depender do `NODE_ENV`. Você pode obter um comportamento semelhante sem o Expo Services escrevendo um script que sobrescreva o **.env.local** ou o **.env** com o conteúdo adequado para o ambiente com o qual deseja trabalhar.

### Desativando variáveis de ambiente \{#disabling-environment-variables}

As variáveis de ambiente no Expo CLI têm duas partes, e ambas podem ser desativadas:

1. O Expo CLI carrega automaticamente os arquivos **.env** no processo global. Para desativar esse comportamento, defina a variável de ambiente `EXPO_NO_DOTENV` como `1` antes de executar qualquer comando do Expo CLI: `EXPO_NO_DOTENV=1`.
2. A configuração do Metro do Expo inclui a serialização embutida das variáveis de ambiente no bundle JavaScript do cliente. Para desativar esse comportamento, use `EXPO_NO_CLIENT_ENV_VARS=1`.

Se você estiver tendo problemas com variáveis de ambiente, pode tentar desativar um ou os dois recursos.

## Variáveis de ambiente no Expo Services \{#environment-variables-in-expo-services}

### Expo Build \{#expo-build}

O [Expo Build](/build/introduction/) usa o Metro Bundler para compilar o bundle JavaScript incorporado ao binário do seu app. Por isso, ele usará os arquivos **.env** enviados com o seu job de build para incorporar as variáveis `EXPO_PUBLIC_` ao seu código. O Expo Build também permite definir variáveis de ambiente dentro dos perfis de build no **eas.json** e no Expo Services. Confira a documentação do Expo Build sobre [variáveis de ambiente e secrets de build](/eas/environment-variables) para mais informações.

### Expo Update \{#expo-update}

O [Expo Update](/eas-update/introduction) usa o Metro Bundler no seu ambiente local ou no CI para compilar o bundle do app. Por isso, ele usará os arquivos **.env** disponíveis para incorporar as variáveis `EXPO_PUBLIC_` ao seu código. Confira a documentação do Expo Update sobre [variáveis de ambiente](/eas/environment-variables/usage/#using-environment-variables-with-expo-update) para mais informações.

## Migrando para as variáveis de ambiente do Expo \{#migrating-to-expo-environment-variables}

### Do react-native-config \{#from-react-native-config}

Atualize os seus arquivos **.env** para adicionar o prefixo `EXPO_PUBLIC_` a todas as variáveis usadas no código JavaScript:

```diff .env
- API_URL=https://myapi.com
+ EXPO_PUBLIC_API_URL=https://myapi.com
```

> Se você tiver arquivos **.env** fora do padrão (por exemplo, **.env.staging**), migre-os para um dos [arquivos **.env** padrão](#using-multiple-env-files-to-define-separate-environments).

Depois, atualize o seu código para usar `process.env.EXPO_PUBLIC_[VARNAME]`:

```diff
- import Config from 'react-native-config';

- const apiUrl = Config.API_URL;
+ const apiUrl = process.env.EXPO_PUBLIC_API_URL;
```

### Do babel-plugin-transform-inline-environment-variables \{#from-babel-plugin-transform-inline-environment-variables}

Usar um plugin do Babel para transformar as referências às variáveis de ambiente no código é parecido com o funcionamento das variáveis de ambiente do Expo. Defina as suas variáveis dentro de um arquivo **.env** e atualize os nomes delas para usar o prefixo `EXPO_PUBLIC_`:

```diff
- const apiUrl = process.env.API_URL;
+ const apiUrl = process.env.EXPO_PUBLIC_API_URL;
```

Depois, você pode remover o plugin da sua [configuração do Babel](/versions/latest/config/babel/):

```diff babel.config.js
module.exports = function (api) {
  api.cache(true);
  return {
    presets: ['babel-preset-expo'],
--    plugins: ['transform-inline-environment-variables'],
  };
};
```

Depois de atualizar o arquivo de configuração do Babel, não deixe de limpar o cache com `npx expo start --clear`.

### Do direnv \{#from-direnv}

Mova as variáveis de ambiente usadas no seu JavaScript do arquivo **.envrc** para um arquivo **.env** e adicione o prefixo `EXPO_PUBLIC_` a elas.

Antes, com o `direnv`, você precisava usar uma [app config dinâmica](/workflow/configuration/#dynamic-configuration) que lia de [`process.env`](https://nodejs.org/dist/latest/docs/api/process.html#process_process_env) para definir variáveis de ambiente no campo `extra` e, assim, usá-las no código JavaScript por meio do [`expo-constants`](/versions/latest/sdk/constants). Mova essas referências diretamente para o seu código, adicionando o prefixo `EXPO_PUBLIC_`:

```diff
- import Constants from 'expo-constants';

- const apiUrl = Constants.expoConfig.extra.apiUrl;
+ const apiUrl = process.env.EXPO_PUBLIC_API_URL;
```

> [`direnv`](https://direnv.net/) carrega e descarrega automaticamente variáveis de ambiente no seu shell de acordo com o diretório atual. Isso significa que ele pode afetar o ambiente de qualquer processo executado nesse diretório, e não apenas o Expo CLI. Você provavelmente vai querer continuar usando o `direnv` para outras variáveis de ambiente que não são usadas no seu código JavaScript.

## Considerações de segurança \{#security-considerations}

Nunca armazene segredos sensíveis em variáveis de ambiente com o prefixo `EXPO_PUBLIC_`. Quando um usuário final executa o seu app, ele tem acesso a todo o código e às variáveis de ambiente incorporadas no app. Leia mais sobre [como armazenar informações sensíveis](https://reactnative.dev/docs/security#storing-sensitive-info).
