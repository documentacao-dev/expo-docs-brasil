Monorepos, ou _"repositórios monolíticos"_, são repositórios únicos que reúnem vários apps ou pacotes. Eles podem acelerar o desenvolvimento de projetos maiores, facilitar o compartilhamento de código e funcionar como uma única fonte de verdade. Este guia configura um monorepo simples com um projeto Expo. O Expo tem suporte de primeira classe para monorepos gerenciados com gerenciadores de pacotes que oferecem workspaces: [Bun](https://bun.sh/docs/install/workspaces), [npm](https://docs.npmjs.com/cli/using-npm/workspaces), [pnpm](https://pnpm.io/workspaces) e [Yarn](https://yarnpkg.com/features/workspaces) (v1 Classic e Berry). O Expo detecta monorepos automaticamente e configura os novos projetos de app adicionados a um monorepo. A detecção é feita com base na configuração de workspaces do seu projeto.

> **info** Monorepos não são para todo projeto. Eles são úteis quando vários apps vivem em um único repositório e compartilham código, ou quando ajudam a manter módulos nativos junto do app. O custo é uma complexidade maior na configuração das ferramentas. Verifique se suas ferramentas e bibliotecas funcionam bem dentro de um monorepo antes de montar um.

<Collapsible summary="Configuração automática (migrando para o SDK 52+)">

<a id="automatic-configuration" />

O Expo configura o Metro automaticamente para monorepos. Você não precisa configurar o Metro manualmente em monorepos se usar o [`expo/metro-config`](/guides/customizing-metro/).

Se você configurou o Metro manualmente para monorepos antes e tem um **metro.config.js** que modifica alguma das propriedades a seguir, remova essas propriedades da configuração:

- `watchFolders`
- `resolver.nodeModulesPath`
- `resolver.extraNodeModules`
- `resolver.disableHierarchicalLookup`

Depois de remover essas opções, execute o Expo com `npx expo start --clear` uma vez para apagar o cache desatualizado do Metro. Se o app continuar funcionando como esperado, ele é um monorepo Node comum e não precisa de nenhuma configuração especial daqui em diante.

</Collapsible>

<Collapsible summary="Configuração manual (antes do SDK 52)">

<a id="manual-configuration" />

A configuração do Metro do Expo tem suporte nativo a monorepos para Bun, npm, pnpm e Yarn. Você não precisa configurar o Metro manualmente em monorepos se usar a configuração de [`expo/metro-config`](/guides/customizing-metro/).

Antes do SDK 52, configurar um monorepo com o Metro exigia duas alterações manuais:

1. O Metro precisava ser configurado manualmente para observar o código dentro do monorepo (por exemplo, não apenas **apps/cool-app**.)
2. A resolução do Metro precisava ser ajustada para encontrar pacotes em outros workspaces e em várias pastas `node_modules` (por exemplo, **apps/cool-app/node_modules** ou **node_modules**.)

A configuração era ajustada [criando um **metro.config.js**](/guides/customizing-metro/#customizing) com o seguinte conteúdo:

```js metro.config.js
const { getDefaultConfig } = require('expo/metro-config');
const path = require('path');

// This can be replaced with `find-yarn-workspace-root`
const monorepoRoot = path.resolve(__dirname, '../..');
const config = getDefaultConfig(__dirname);

// 1. Watch all files within the monorepo
config.watchFolders = [monorepoRoot];
// 2. Let Metro know where to resolve packages and in what order
config.resolver.nodeModulesPaths = [
  path.resolve(projectRoot, 'node_modules'),
  path.resolve(monorepoRoot, 'node_modules'),
];

module.exports = config;
```

> Saiba mais sobre [como personalizar o Metro](/guides/customizing-metro).

## Configurar um monorepo \{#setting-up-a-monorepo}

Em um monorepo, o app normalmente fica em um subdiretório do repositório, e o gerenciador de pacotes é configurado para permitir adicionar dependências a outros pacotes de dentro do monorepo.
Por exemplo, a estrutura básica de um monorepo com apps Expo pode ser assim:

- **apps**: contém vários projetos, incluindo apps Expo.
- **packages**: contém os diferentes pacotes usados pelos apps.
- **package.json**: arquivo de pacote da raiz.

Todo monorepo deve ter um arquivo **package.json** "raiz". Ele é a configuração principal do monorepo e pode conter ferramentas instaladas para todos os projetos do repositório. Dependendo do gerenciador de pacotes que você usa, os passos para configurar os workspaces podem variar. Para [Bun](https://bun.sh/docs/install/workspaces), [npm](https://docs.npmjs.com/cli/using-npm/workspaces) e [Yarn](https://yarnpkg.com/features/workspaces), adicione uma propriedade `workspaces` ao **package.json** da raiz, especificando [padrões glob](https://classic.yarnpkg.com/lang/en/docs/workspaces/#toc-tips-tricks) para todos os workspaces do monorepo:

```json package.json
{
  "name": "monorepo",
  "private": true,
  "version": "0.0.0",
  "workspaces": ["apps/*", "packages/*"]
}
```

Para o [pnpm](https://pnpm.io/workspaces), em vez disso, crie um arquivo [**pnpm-workspace.yaml**](https://pnpm.io/pnpm-workspace_yaml):

```yaml pnpm-workspace.yaml
packages:
  - 'apps/*'
  - 'packages/*'
```

### Criar o primeiro app \{#create-your-first-app}

Agora que a estrutura básica do monorepo está pronta, adicione o primeiro app.

Antes de criar o app, crie o diretório **apps**. Ele contém todos os apps ou sites separados que pertencem a este monorepo. Dentro dele, você pode criar um subdiretório para o app Expo.

<Terminal
  cmd={{
    npm: ['$ npx create-expo-app@latest apps/cool-app'],
    yarn: ['$ yarn create expo-app apps/cool-app'],
    pnpm: ['$ pnpm create expo-app apps/cool-app'],
    bun: ['$ bun create expo apps/cool-app'],
  }}
/>

> Se você já tem um app, pode copiar todos os arquivos dele para um diretório dentro de **apps**.

Depois de copiar ou criar o primeiro app, instale as dependências com o gerenciador de pacotes a partir do diretório raiz do monorepo para verificar avisos comuns.

### Criar um pacote \{#create-a-package}

Monorepos ajudam a agrupar código em um único repositório. Isso inclui apps, mas também pacotes separados, que também não precisam ser publicados. O [repositório do Expo](https://github.com/expo/expo) também usa essa abordagem. Todos os pacotes do SDK do Expo ficam dentro do diretório [**packages**](https://github.com/expo/expo/tree/main/packages) do nosso repositório. Isso nos ajuda a testar o código de um dos nossos diretórios de [**apps**](https://github.com/expo/expo/tree/main/apps/native-component-list) antes de publicá-lo.

Vamos voltar à raiz e criar o diretório **packages**. Ele pode conter todos os pacotes separados que você quiser criar. Dentro dele, adicione um novo subdiretório. Esse subdiretório é um pacote separado que pode ser usado dentro do app. No exemplo abaixo, o chamamos de **cool-package**.

<Terminal
  cmd={{
    npm: ['$ mkdir -p packages/cool-package && cd packages/cool-package && npm init'],
    yarn: ['$ mkdir -p packages/cool-package && cd packages/cool-package && yarn init'],
    pnpm: ['$ mkdir -p packages/cool-package && cd packages/cool-package && pnpm init'],
    bun: ['$ mkdir -p packages/cool-package && cd packages/cool-package && bun init -y'],
  }}
/>

Não vamos entrar em muitos detalhes sobre como criar um pacote. Se você não estiver familiarizado com isso, considere usar um app simples, sem monorepos. Mas, para tornar o exemplo completo, vamos adicionar um arquivo **index.js** com o seguinte conteúdo:

```js index.js
export const greeting = 'Hello!';
```

### Usar o pacote \{#using-the-package}

Como em pacotes comuns, precisamos adicionar o **cool-package** como dependência do **cool-app**. A principal diferença entre um pacote comum e um pacote do monorepo é que você sempre vai querer usar o _"estado atual do pacote"_ em vez de uma versão. Vamos adicionar o **cool-package** ao app incluindo `"cool-package": "*"` no arquivo **package.json** do app:

```json package.json
{
  "name": "cool-app",
  "version": "1.0.0",
  "scripts": {
    "start": "expo start",
    "android": "expo start --android",
    "ios": "expo start --ios",
    "web": "expo start --web"
  },
  "dependencies": {
    "cool-package": "*",
    "expo": "~{{expoSdkVersion}}",
    "expo-status-bar": "~55.0.0",
    "react": "{{reactVersion}}",
    "react-native": "{{reactNativeVersion}}"
  }
}
```

Bun, npm e pnpm aceitam especificar dependências de workspace usando `"workspace:*"` em vez de `"*"`. Isso garante que o pacote do workspace nunca resolva um pacote publicado de mesmo nome no registro do npm. Essa opção é opcional.

Depois de adicionar o pacote, instale as dependências com o gerenciador de pacotes a partir do diretório raiz do monorepo para verificar avisos comuns mais uma vez.

Agora você já deve conseguir usar o pacote dentro do app! Para testar, edite o **App.js** e renderize o texto `greeting` do **cool-package**.

```jsx App.js
import { greeting } from 'cool-package';
import { StatusBar } from 'expo-status-bar';
import React from 'react';
import { Text, View } from 'react-native';

export default function App() {
  return (
    <View style={{ flex: 1, alignItems: 'center', justifyContent: 'center' }}>
      <Text>{greeting}</Text>
      <StatusBar style="auto" />
    </View>
  );
}
```

## Problemas comuns \{#common-issues}

Monorepos podem causar problemas de resolução e de dependências que um projeto comum não teria. Eles exigem conhecimento mais aprofundado e configuração específica das ferramentas. Você assume mais complexidade e vai precisar resolver problemas que não existiriam sem workspaces. Veja alguns problemas comuns que você pode encontrar.

### Gerenciadores de pacotes com dependências isoladas \{#package-managers-with-isolated-dependencies}

> **info** A partir do **SDK 54**, o Expo oferece suporte a dependências isoladas e instalações isoladas.<br />
> Com o **SDK 53**, recomenda-se desativar as dependências isoladas, ou você pode encontrar erros de build nativo e conflitos de dependências.

[Bun](https://bun.com/docs/install/isolated) e [pnpm](https://pnpm.io/settings#nodelinker) têm suporte de primeira classe a instalações isoladas. No caso do pnpm, essa é a estratégia de instalação padrão, a menos que seja desativada.

Com dependências isoladas, os gerenciadores de pacotes não elevam (hoisting) pacotes de diretórios `node_modules` aninhados para níveis superiores. Em vez disso, eles criam um diretório central que contém seus módulos Node e criam links para esse diretório. Essa estrutura de dependências obriga os pacotes a acessar apenas as dependências que declaram explicitamente. É uma estratégia de instalação bem mais rigorosa que a estratégia tradicional **hoisted**, padrão do npm e do Yarn, que instala as dependências em uma estrutura achatada.

Um efeito colateral das instalações **hoisted** é que você pode depender, sem perceber, de módulos Node que não estão nas `dependencies` ou `peerDependencies` do seu próprio **package.json**. Assim, muitas outras dependências, das quais outros pacotes dependem, ficam elevadas e acessíveis para você. Isso pode causar comportamento não determinístico e permitir cadeias de dependências quebradas, que são mais frágeis e podem gerar erros de resolução ao atualizar ou fazer upgrade de pacotes. Isso é especialmente comum em monorepos.

**A partir do SDK 54**, o Expo oferece suporte a dependências isoladas. Infelizmente, nem todos os pacotes que você instalar vão funcionar, e algumas bibliotecas do React Native podem causar erros de build ou de resolução com dependências isoladas. Se encontrar problemas com instalações isoladas usando o [pnpm](https://pnpm.io/settings#nodelinker), mude para a estratégia de instalação **hoisted** alterando a configuração `nodeLinker` no arquivo **pnpm-workspace.yaml** na raiz do repositório:

```yaml pnpm-workspace.yaml
nodeLinker: hoisted
```

### Pacotes nativos duplicados em monorepos \{#duplicate-native-packages-within-monorepos}

O Expo tem suporte aprimorado a padrões mais completos de **node_modules**, como módulos isolados. Infelizmente, se o app tiver dependências duplicadas, problemas ainda podem ocorrer:

- Versões duplicadas do React Native em um mesmo monorepo não têm suporte
- Versões duplicadas do React em um mesmo app causam erros de runtime
- Versões duplicadas dos módulos Turbo e Expo podem causar erros de runtime ou de build

Você pode verificar se o monorepo tem várias versões de um pacote, por exemplo `react-native`, e descobrir por que elas estão instaladas com o gerenciador de pacotes que você usa.

<Terminal
  cmd={{
    npm: ['$ npm why react-native'],
    yarn: ['$ yarn why react-native'],
    pnpm: ['$ pnpm why --depth=10 react-native'],
    bun: ['$ bun pm why react-native'],
  }}
/>

A saída desses comandos varia bastante de um gerenciador de pacotes para outro, mas você pode identificar pacotes duplicados em qualquer uma delas procurando por várias versões do pacote, por exemplo `react-native@0.79.5` e `react-native@0.81.0`.

#### Adicionar resoluções para dependências peer \{#adding-dependency-resolutions-for-peer-dependencies}

Se a dependência duplicada não puder ser resolvida alterando as dependências do projeto, pode ser necessário adicionar uma resolução. Por exemplo, nem todos os pacotes atualizaram seus **peerDependencies** para oferecer suporte ao React 19. Para contornar isso, você pode criar uma resolução que force a instalação de uma única versão do `react`.

```json package.json
{
  "name": "monorepo",
  "private": true,
  "version": "0.0.0",
  "workspaces": ["apps/*", "packages/*"],
  "resolutions": {
    "react": "^{{reactVersion}}"
  }
}
```

Para o [npm](https://docs.npmjs.com/cli/v9/configuring-npm/package-json#overrides), você precisa usar uma propriedade chamada `overrides` em vez de `resolutions`.

#### Deduplicar módulos nativos com autolinking \{#deduplicating-auto-linked-native-modules}

Muitas vezes, dependências duplicadas não causam nenhum problema. No entanto, módulos nativos nunca devem ser duplicados, porque apenas uma versão de um módulo nativo pode ser compilada para um build do app por vez. Diferentemente das dependências JavaScript, os builds nativos não conseguem conter duas versões conflitantes de um mesmo módulo nativo.

A partir do **SDK 54**, você pode definir `experiments.autolinkingModuleResolution` como `true` no **app.json** para aplicar o autolinking automaticamente ao Expo CLI e ao bundler Metro. Isso força as dependências que o Metro resolve a corresponderem aos módulos nativos que o [autolinking](/modules/autolinking/) vincula aos builds nativos.

A partir do **SDK 55**, isso é ativado automaticamente para apps em monorepos.

Pacotes que não são módulos nativos também podem quebrar quando são duplicados. Uma biblioteca que cria um contexto do React é um exemplo comum. Para aplicar as mesmas verificações e a mesma resolução a esses pacotes, veja [Verificando pacotes que não são módulos nativos](/modules/autolinking/#checking-packages-that-arent-native-modules).

### Script '...' não existe \{#script--does-not-exist}

O React Native usa pacotes para distribuir arquivos JavaScript e arquivos nativos. Esses arquivos nativos também precisam ser vinculados, como o arquivo [**react-native/react.gradle**](https://github.com/facebook/react-native/blob/v0.70.6/react.gradle) em **android/app/build.gradle**. Normalmente, esse caminho fica fixo em algo como:

**Android** ([fonte](https://github.com/facebook/react-native/blob/e918362be3cb03ae9dee3b8d50a240c599f6723f/template/android/app/build.gradle#L84))

```groovy
apply from: "../../node_modules/react-native/react.gradle"
```

**iOS** ([fonte](https://github.com/facebook/react-native/blob/e918362be3cb03ae9dee3b8d50a240c599f6723f/template/ios/Podfile#L1))

```ruby
require_relative '../node_modules/react-native/scripts/react_native_pods'
```

Infelizmente, esse caminho pode ser diferente em monorepos por causa do [hoisting](https://classic.yarnpkg.com/blog/2018/02/15/nohoist/). Ele também não usa a [resolução de módulos do Node](https://nodejs.org/api/modules.html#all-together). Você pode evitar esse problema usando o Node para encontrar a localização do pacote, em vez de fixar o caminho:

**Android** ([fonte](https://github.com/expo/expo/blob/6877c1f5cdca62b395b0d5f49d87f2f3dbb50bec/templates/expo-template-bare-minimum/android/app/build.gradle#L87))

```groovy
apply from: new File(["node", "--print", "require.resolve('react-native/package.json')"].execute(null, rootDir).text.trim(), "../react.gradle")
```

**iOS** ([fonte](https://github.com/expo/expo/blob/61cbd9a5092af319b44c319f7d51e4093210e81b/templates/expo-template-bare-minimum/ios/Podfile#L2))

```ruby
require File.join(File.dirname(`node --print "require.resolve('react-native/package.json')"`), "scripts/react_native_pods")
```

Nos trechos acima, você pode ver que usamos o método [`require.resolve()`](https://nodejs.org/api/modules.html#requireresolverequest-options) do próprio Node para encontrar a localização do pacote. Referenciamos explicitamente o `package.json` porque queremos encontrar a localização raiz do pacote, não a do ponto de entrada. Com essa localização raiz, podemos resolver o caminho relativo esperado dentro do pacote. [Saiba mais sobre essas referências aqui](https://github.com/expo/expo/blob/main/packages/expo-modules-core/README.md).

Todos os módulos e templates do SDK do Expo têm essas referências dinâmicas e funcionam com monorepos. No entanto, às vezes você pode encontrar pacotes que ainda usam o caminho fixo. Você pode editá-lo manualmente com o [`patch-package`](https://github.com/ds300/patch-package#readme) ou avisar os mantenedores do pacote.
