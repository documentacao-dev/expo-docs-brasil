---
title: Por que Metro?
description: Saiba por que o Metro é o futuro do bundling universal no React Native e como ele beneficia os developers.
---

[Metro](https://metrobundler.dev/) é o bundler oficial do Expo e do React Native. Ele é uma ferramenta de build central no framework Expo. Bundlers envolvem milhares de decisões e trade-offs. Este documento apresenta os principais motivos pelos quais o Expo é desenvolvido em torno do Metro e como isso beneficia os developers.

## Bundler oficial da Meta \{#official-meta-bundler}

O Metro é mantido pela Meta, responsável pelo React, React Native, Yoga e Hermes. Ele é usado para desenvolver alguns dos maiores apps do mundo, de todas as categorias nas lojas de apps.

Os engenheiros da Meta desenvolvem o Metro ativamente, com o requisito explícito de empacotar todos os seus apps, com mais de 400 mil arquivos de código-fonte, mantendo-o rápido e confiável.

Por ter suporte de primeira classe ao Metro, garantimos que os developers do Expo tenham continuidade nas ferramentas da Meta e acesso imediato a recursos emergentes. Isso inclui:

- O React Fast Refresh [foi lançado pela primeira vez](https://reactnative.dev/blog/2019/09/18/version-0.61) como um recurso do Metro em 2019. A comunidade web do React adotou o recurso no ano seguinte, via Webpack.
- Transformação de JavaScript em bytecode Hermes para uma inicialização nativa instantânea.
- O React Native DevTools, incluindo suporte de primeira classe a [debug de rede e de JS](/debugging/tools/#debugging-with-react-native-devtools), está disponível exclusivamente com Metro e Hermes.
- O React Compiler foi lançado inicialmente como um plugin Babel compatível com o Metro.

Entre os recursos novos e os planejados para o Metro estão:

- Compilação de código Flow para código de máquina nativo com o Static Hermes. Saiba mais na palestra [Static Hermes](https://www.youtube.com/watch?v=GUM64b-gAGg), de Tzvetan Mikov.
- Busca de dados, streaming, React Suspense, renderização no servidor e renderização estática em tempo de build com React Server Components universais para todas as plataformas. Saiba mais na palestra [Universal React Server Components](https://www.youtube.com/watch?v=djhEgxQf3Kw), na React Conf 2024.

A equipe do Expo colabora com a Meta para desenvolver o Metro para o Expo Router, adicionando recursos como [roteamento baseado em arquivos](/develop/app-navigation/), [suporte à web](/guides/customizing-metro/#web-support), [divisão de bundle](/guides/customizing-metro/#bundle-splitting), [tree shaking](/guides/tree-shaking/), [CSS](/versions/latest/config/metro/#css), [componentes DOM](/guides/dom-components/), server components e [rotas de API](/router/web/api-routes/).

## Testado em larga escala \{#battle-tested-at-scale}

Quase todo app React Native do mundo usa o Metro, o que faz dele uma solução testada em produção e otimizada para projetos de grande escala. Isso o torna adequado para developers de todos os portes, de entusiastas a grandes empresas. O Metro foi projetado especificamente para lidar com os apps de grande escala da Meta, e por isso tem recursos como delta bundling e [caches remotos compartilhados](https://metrobundler.dev/docs/caching).

## Processamento sob demanda \{#on-demand-processing}

Em desenvolvimento, o Metro não faz nenhum trabalho específico de plataforma até que seja solicitado. Isso permite que os developers trabalhem em projetos grandes sem pagar um custo de performance pelo número de plataformas que têm suporte. Combinado com um cache agressivo e [rotas assíncronas](/router/web/async-routes/), os developers podem fazer o bundle, de forma incremental, somente das partes do app em que estão trabalhando.

## Multidimensional \{#multi-dimensional}

Ao contrário dos bundlers tradicionais, que criam várias instâncias para fazer o bundle do código de servidor e de cliente, o Metro maximiza o reaproveitamento de recursos entre plataformas e ambientes (servidor, cliente, componentes DOM). Essa arquitetura é ideal para desenvolvimento multiplataforma e de servidor.

## Memoização de transformações reutilizável \{#reusable-transform-memoization}

O Metro é incremental e pode criar artefatos de transformação em cache que podem ser usados em diferentes máquinas. Isso permite que times grandes reaproveitem trabalho de builders remotos, uma técnica usada pela Meta em todos os projetos grandes.

## Otimizado para runtimes personalizados \{#optimized-for-custom-runtimes}

Enquanto outros bundlers são projetados em torno da especificação estática dos navegadores web, o Metro é otimizado para a flexibilidade do React Native. Isso permite recursos como gerar o conjunto específico de recursos da linguagem com suporte pela compilação de bytecode Hermes, o que torna a inicialização do app em produção mais rápida. Isso também vai se estender ao Static Hermes, que vai compilar informações de tipo estáticas em código de máquina para apps nativos.

## Suporte entre tecnologias \{#cross-technology-support}

O Expo aproveita a tecnologia do Metro para criar funcionalidades inovadoras, como [componentes DOM](/guides/dom-components/). Isso permite que um componente React em um app nativo seja empacotado dinamicamente como um site inteiro, com os mesmos padrões do app pai, sob demanda.

## Exportação de assets nativos \{#native-asset-exports}

Ao contrário dos bundlers tradicionais, em que o resultado final é um app totalmente hospedado, as opções de configuração do Metro permitem exportar bundles para incorporar como artefatos nativos em binários de apps independentes. Isso aproveita otimizações específicas de cada sistema operacional, como `xcassets` nas plataformas da Apple.

## Processamento concorrente \{#concurrent-processing}

Toda a transformação de AST no Metro é feita de forma concorrente em todas as threads disponíveis, maximizando o uso do hardware.

## Comparação com outras abordagens \{#comparison-with-other-approaches}

Embora o Metro seja projetado para o desenvolvimento de apps universais, ele costuma ser comparado com bundlers voltados apenas para a web. Estas são algumas das principais diferenças:

### ESM do navegador versus bundling \{#browser-esm-versus-bundling}

Enquanto bundlers como o Vite aproveitam o suporte nativo a ESM do navegador, essa abordagem pode levar a tempos de desenvolvimento mais lentos, em projetos de médio a grande porte, por causa de milhares de requisições de rede em cascata. O Metro faz o bundling no desenvolvimento local, o que aproxima muito mais os resultados do desenvolvimento dos resultados de produção, e é mais adequado para o número maior de módulos do React Native.

### JavaScript versus linguagens nativas \{#javascript-versus-native-languages}

Vários bundlers estão optando por escrever seu núcleo em Rust por motivos de performance, mas isso traz alguns trade-offs, como contribuições, patches e desenvolvimento mais difíceis. O Metro usa uma combinação de tecnologias de acordo com a operação:

- O bundler principal e os utilitários são escritos em JS/Flow.
- A observação de arquivos usa um crawler em JS por padrão, e pode usar o Watchman (C++) quando estiver instalado.
- A AST é analisada pelo parser Hermes (WebAssembly) em um formato compatível com o Babel.
- A transformação da AST é feita com Babel. Isso maximiza a personalização para o developer.
- A minificação usa o Hermes em plataformas nativas e o Terser (com suporte opcional ao ESBuild) para a web.
- O parsing e a minificação de CSS são feitos com o [LightningCSS](https://lightningcss.dev/) (Rust).

Essa abordagem acompanha as ferramentas que a Meta e a comunidade usam, e torna mais fácil fazer debug, profiling e patches para os developers.
