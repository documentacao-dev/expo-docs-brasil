Para compilar o seu projeto em um app na sua própria máquina, você precisa gerar manualmente o código nativo antes de testar um debug build ou criar um build de produção para enviar às lojas de apps. Há duas formas de compilar o seu app localmente. Este guia traz uma introdução breve aos dois métodos e referências para os outros guias necessários para montar esse fluxo de trabalho.

## Compilação local do app \{#local-app-compilation}

Para compilar o seu projeto localmente, use os comandos de compilação da Expo CLI, que geram os diretórios **android** e **ios**:

<Terminal
  cmd={{
    npm: [
      '# Build native Android project',
      '$ npx expo run:android',
      '# Build native iOS project',
      '$ npx expo run:ios',
    ],
    yarn: [
      '# Build native Android project',
      '$ yarn expo run:android',
      '# Build native iOS project',
      '$ yarn expo run:ios',
    ],
    pnpm: [
      '# Build native Android project',
      '$ pnpm expo run:android',
      '# Build native iOS project',
      '$ pnpm expo run:ios',
    ],
    bun: [
      '# Build native Android project',
      '$ bun expo run:android',
      '# Build native iOS project',
      '$ bun expo run:ios',
    ],
  }}
/>

Os comandos acima compilam o seu projeto, usando o Android SDK ou o Xcode instalados na sua máquina, em um debug build do seu app. Cada comando faz duas etapas: compila e instala o binário nativo no seu dispositivo ou emulador, e depois inicia o Metro bundler para servir o seu código JavaScript ou TypeScript.

- Esses comandos de compilação executam primeiro o `npx expo prebuild` para gerar os diretórios nativos (**android** e **ios**) antes do build, caso eles ainda não existam. Se já existirem, essa etapa é ignorada.
- Você também pode usar a flag `--device` para escolher o dispositivo em que o app será executado. Pode ser um dispositivo conectado fisicamente ou um emulador/simulador.
- Você pode passar `--variant release` (Android) ou `--configuration Release` (iOS) para gerar um [build de produção do seu app](/deploy/build-project/#release-builds-locally). Esses builds não são assinados e não podem ser enviados às lojas de apps. Para assinar o seu build de produção, veja [Produção local do app](/guides/local-app-production/).
- **Somente Android**: a partir da SDK 54, você pode usar a variante `--variant debugOptimized` para iterar mais rápido no desenvolvimento. Veja [Compilando Android na referência da Expo CLI](/more/expo-cli/#compiling-android) para mais informações.

### Depois do primeiro build: use o `npx expo start` \{#after-the-first-build-use-npx-expo-start}

Depois que o app estiver compilado e instalado no seu dispositivo ou emulador, você não precisa refazer o build a cada alteração. Se você estiver modificando apenas código JavaScript ou TypeScript, pode iniciar o Metro bundler sozinho:

<Terminal
  cmd={{
    npm: ['$ npx expo start'],
    yarn: ['$ yarn expo start'],
    pnpm: ['$ pnpm expo start'],
    bun: ['$ bun expo start'],
  }}
/>

Depois, pressione <kbd>A</kbd> para Android ou <kbd>I</kbd> para iOS no terminal para abrir o app já instalado. O Metro serve o bundle JavaScript atualizado sem recompilar o código nativo, então o app carrega em segundos em vez de minutos.

| Comando                                     | O que faz                                             | Quando usar                                                                      |
| ------------------------------------------- | ----------------------------------------------------- | -------------------------------------------------------------------------------- |
| `npx expo run:android` / `npx expo run:ios` | Compila o código nativo, instala o app e inicia o Metro. | Primeiro build, depois de adicionar uma biblioteca nativa ou depois de alterar um config plugin. |
| `npx expo start`                            | Inicia apenas o Metro bundler.                        | No dia a dia, quando você altera apenas código JavaScript ou TypeScript.         |

Para alterar a configuração do projeto ou o código nativo depois do primeiro build, você precisará refazer o build com `npx expo run:android|ios`. Executar `npx expo prebuild` de novo aplica as mudanças por cima dos arquivos existentes. Isso também pode gerar resultados diferentes após o build.

Para evitar isso, os diretórios nativos são adicionados automaticamente ao **.gitignore** do projeto quando você cria um novo projeto, e você pode usar o comando `npx expo prebuild --clean`. Assim o projeto fica sempre gerenciado, e a [flag `--clean`](/workflow/continuous-native-generation/#clean) apaga os diretórios existentes antes de gerá-los novamente. Você pode usar o [app config](/workflow/configuration/) ou criar um [config plugin](/config-plugins/introduction/) para modificar a configuração ou o código do projeto dentro dos diretórios nativos.

## Builds locais com `expo-dev-client` \{#local-builds-with-expo-dev-client}

Se você instalar o [`expo-dev-client`](/develop/development-builds/introduction/) no seu projeto, o debug build vai incluir a interface e as ferramentas do `expo-dev-client`. Chamamos esses builds de development builds.

<Terminal
  cmd={{
    npm: ['$ npx expo install expo-dev-client'],
    yarn: ['$ yarn expo install expo-dev-client'],
    pnpm: ['$ pnpm expo install expo-dev-client'],
    bun: ['$ bun expo install expo-dev-client'],
  }}
/>

Para criar um development build, use os comandos de [compilação local do app](#local-app-compilation) (`npx expo run:[android|ios]`), que criam um debug build e iniciam o servidor de desenvolvimento.

## Builds locais com product flavors do Android \{#local-builds-using-android-product-flavors}

Se você tem um projeto Android personalizado com vários product flavors que usam application IDs diferentes, pode configurar o `npx expo run:android` para usar o flavor e o build type corretos. O Expo oferece suporte tanto a `--variant` quanto a `--app-id` para personalizar o comportamento de build e de execução.

A flag `--variant` pode trocar o build type do Android de **debug** para **release**. Ela também pode configurar um product flavor e um build type, quando escrito em camelCase. Por exemplo, se você tiver os product flavors [**free** e **paid**](https://developer.android.com/build/build-variants#change-app-id), pode criar uma versão de desenvolvimento do seu app com:

<Terminal
  cmd={{
    npm: [
      '$ npx expo run:android --variant freeDebug',
      '',
      '$ npx expo run:android --variant paidDebug',
    ],
    yarn: [
      '$ yarn expo run:android --variant freeDebug',
      '',
      '$ yarn expo run:android --variant paidDebug',
    ],
    pnpm: [
      '$ pnpm expo run:android --variant freeDebug',
      '',
      '$ pnpm expo run:android --variant paidDebug',
    ],
    bun: [
      '$ bun expo run:android --variant freeDebug',
      '',
      '$ bun expo run:android --variant paidDebug',
    ],
  }}
/>

A flag `--app-id` pode ser usada para abrir o app depois do build, usando um application id personalizado. Por exemplo, se o seu product flavor **free** usa `applicationIdSuffix ".free"` ou `applicationId "dev.expo.myapp.free"`, você pode fazer o build e abrir o app com:

<Terminal
  cmd={{
    npm: ['$ npx expo run:android --variant freeDebug --app-id dev.expo.myapp.free'],
    yarn: ['$ yarn expo run:android --variant freeDebug --app-id dev.expo.myapp.free'],
    pnpm: ['$ pnpm expo run:android --variant freeDebug --app-id dev.expo.myapp.free'],
    bun: ['$ bun expo run:android --variant freeDebug --app-id dev.expo.myapp.free'],
  }}
/>

> **info** Também é possível personalizar o build type do Android, mas isso quebraria a premissa do Expo de que o build type **release** é usado em produção. Você poderia gerar código não otimizado no app usando um build type diferente de **release**.
