Os tempos de build nativo podem deixar o fluxo de desenvolvimento mais lento. O Expo oferece versões pré-compiladas dos seus módulos mais complexos, para que o projeto vincule binários pré-compilados em vez de recompilá-los a partir do código-fonte a cada build. No Android, esses binários vêm como arquivos **.aar** vinculados pelo Gradle. No iOS, vêm como `XCFrameworks` vinculados pelo CocoaPods. Ambos estão incluídos nos pacotes npm normais do Expo. Pacotes que ainda não têm versão pré-compilada voltam a ser compilados a partir do código-fonte automaticamente, então módulos pré-compilados e módulos compilados a partir do código-fonte coexistem no mesmo projeto.

**A maioria dos projetos não precisa fazer nada.** Os módulos Expo pré-compilados são ativados automaticamente em projetos novos e existentes com uma versão de SDK compatível.

- **Android**: ativado por padrão desde o SDK 53.
- **iOS**: ativado por padrão no SDK 56 e superiores. No SDK 55, ativado por padrão apenas no Expo Build. Defina `EXPO_USE_PRECOMPILED_MODULES=1` no shell para ativar em builds locais.

<Collapsible summary="Desativando no iOS">

Defina a propriedade `ios.usePrecompiledModules` do config plugin [`expo-build-properties`](/versions/latest/sdk/build-properties/) como `false` para compilar todos os módulos Expo a partir do código-fonte. Isso vale tanto para builds locais quanto para o Expo Build, e passa a valer na próxima vez que você executar `npx expo prebuild`:

```json app.json
{
  "expo": {
    "plugins": [
      [
        "expo-build-properties",
        {
          "ios": {
            "usePrecompiledModules": false
          }
        }
      ]
    ]
  }
}
```

Como alternativa, você pode controlar isso diretamente pela variável de ambiente `EXPO_USE_PRECOMPILED_MODULES`, que é lida durante o `pod install`. Para builds locais, exporte-a no shell antes de executar `pod install` (ou `npx expo run:ios`):

<Terminal cmd={['$ export EXPO_USE_PRECOMPILED_MODULES=0']} />

Para o Expo Build, crie uma [variável de ambiente do Expo Services](/eas/environment-variables/manage/):

<Terminal
  cmd={['$ eas env:set --name EXPO_USE_PRECOMPILED_MODULES --value 0 --visibility plaintext']}
/>

A CLI vai pedir que você selecione em quais ambientes (`development`, `preview`, `production`) a variável se aplica.

</Collapsible>

<Collapsible summary="Desativando módulos específicos pelo Expo Autolinking">

Configure o Expo Autolinking com `buildFromSource` no **package.json**. Use `".*"` para desativar todos os módulos pré-compilados, ou liste nomes de pacotes específicos. A mesma configuração está disponível para `android` e `ios`:

{/* prettier-ignore */}
```json package.json
{
  "name": "your-app-name",
  "expo": {
    "autolinking": {
      "android": {
        "buildFromSource": [".*"]
      },
      "ios": {
        "buildFromSource": [".*"]
      }
    }
  }
}
```

Isso normalmente só é necessário quando você mesmo modifica o código-fonte de um módulo, ou quando usa uma opção de config plugin que controla a compilação nativa. Os artefatos pré-compilados vêm com as opções de build padrão de cada módulo, então opções que adicionam ou removem dependências nativas (como o [`barcodeScannerEnabled`](/versions/latest/sdk/camera/#configuration-in-app-config) do `expo-camera` no Android) só têm efeito quando o módulo é compilado a partir do código-fonte.

</Collapsible>

<Collapsible summary="Solução de problemas do Expo Build">

### iOS \{#ios}

No Expo Build, bibliotecas de terceiros como `react-native-reanimated` e `react-native-worklets` são baixadas automaticamente como XCFrameworks pré-compilados. O `pod install` local não baixa esses pacotes por padrão. Esses pacotes são compilados localmente a partir do código-fonte e aplicam automaticamente quaisquer sobrescritas de `staticFeatureFlags`, então divergências de flags e de versão aparecem principalmente no Expo Build. Evite ativar downloads pré-compilados de terceiros para builds locais e mantenha esse caminho restrito ao Expo Build.

#### `react-native-reanimated` e `react-native-worklets` \{#react-native-reanimated-and-react-native-worklets}

Esses dois pacotes são fortemente acoplados. O `react-native-reanimated` vincula o `react-native-worklets` no nível nativo.

**Desative os dois juntos.** Se você precisar de um build a partir do código-fonte de qualquer um dos pacotes (por exemplo, para aplicar um patch ou modificar código nativo), liste os dois em `buildFromSource`. Compilar apenas um a partir do código-fonte gera uma vinculação mista, pré-compilada e de código-fonte, que não consegue resolver o framework correspondente em tempo de execução:

{/* prettier-ignore */}
```json package.json
{
  "expo": {
    "autolinking": {
      "ios": {
        "buildFromSource": ["react-native-reanimated", "react-native-worklets"]
      }
    }
  }
}
```

**Feature flags personalizadas exigem build a partir do código-fonte.** Os valores das feature flags são incorporados ao binário pré-compilado no momento do build, então quaisquer sobrescritas de `worklets.staticFeatureFlags` ou `reanimated.staticFeatureFlags` no **package.json** são ignoradas. Para aplicá-las, desative os módulos pré-compilados com `EXPO_USE_PRECOMPILED_MODULES=0`.

**Quando olhar aqui.** Erros de runtime como `Unable to recognize flag: <NAME>` no Expo Build (mas não localmente) indicam que a lista de flags do artefato pré-compilado não corresponde à versão fixada do pacote. Use o `buildFromSource` acima e [abra uma issue no GitHub](https://github.com/expo/expo/issues).

</Collapsible>
