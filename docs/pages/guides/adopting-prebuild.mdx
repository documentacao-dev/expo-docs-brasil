Este guia mostra como adotar o Expo Prebuild em um projeto criado com `npx @react-native-community/cli@latest init`. Para saber o que o Expo Prebuild faz e quando usá-lo, veja [Continuous Native Generation (CNG)](/workflow/continuous-native-generation/). O tempo necessário para converter o projeto depende da quantidade de alterações nativas personalizadas que você fez nos projetos Android e iOS. Em um projeto novo, isso pode levar um ou dois minutos. Em um projeto grande, vai levar bem mais.

Adotar o prebuild adiciona automaticamente suporte ao desenvolvimento de módulos com a [API de módulos nativos do Expo][expo-modules-core], ao vincular o `expo-modules-core` nativamente. Você também pode usar qualquer comando da [Expo CLI][cli] no projeto.

> **warning** [Nem todas as versões do `react-native` têm suporte explícito](/versions/latest/#each-expo-sdk-version-depends-on-a-react-native-version). Use uma versão do `react-native` que tenha uma versão correspondente do SDK do Expo.

## Instalar o pacote `expo` \{#install-the-expo-package}

O pacote `expo` contém o comando [`npx expo prebuild`](/more/expo-cli/#prebuild) e indica qual [template de prebuild](/workflow/continuous-native-generation#templates) usar:

<Terminal
  cmd={{
    npm: ['$ npm install expo'],
    yarn: ['$ yarn add expo'],
    pnpm: ['$ pnpm add expo'],
    bun: ['$ bun add expo'],
  }}
/>

Instale a versão do `expo` compatível com a [versão do `react-native`](/versions/latest/#each-expo-sdk-version-depends-on-a-react-native-version) que já está instalada no projeto.

## Atualizar o arquivo de entrada \{#update-the-entry-file}

Altere o arquivo de entrada para usar o [`registerRootComponent`](/versions/latest/sdk/expo/#registerrootcomponentcomponent) em vez de `AppRegistry.registerComponent`:

<DiffBlock
  raw={`diff --git a/index.js b/index.js
index 0000000..1111111 100644
--- a/index.js
+++ b/index.js
@@ -1,5 +1,4 @@
-import {AppRegistry} from 'react-native';
-import {name as appName} from './app.json';
+import {registerRootComponent} from 'expo';
 import App from './App';
-
-AppRegistry.registerComponent(appName, () => App);
+registerRootComponent(App);`}
/>

> Saiba mais sobre o [`registerRootComponent`](/versions/latest/sdk/expo/#registerrootcomponentcomponent).

## Prebuild \{#prebuild}

> **warning** Se quiser reverter alterações, faça commit delas antes. O comando também avisa sobre isso!

Se você estiver migrando um projeto existente, veja antes [**como migrar as personalizações nativas**](#migrate-native-customizations).

Execute o comando a seguir para regenerar os diretórios **android** e **ios** com base no app config (**app.json/app.config.js**):

<Terminal
  cmd={{
    npm: ['$ npx expo prebuild --clean'],
    yarn: ['$ yarn expo prebuild --clean'],
    pnpm: ['$ pnpm expo prebuild --clean'],
    bun: ['$ bun expo prebuild --clean'],
  }}
/>

Você pode testar se tudo funcionou fazendo o build dos projetos localmente:

<Terminal
  cmd={{
    npm: [
      '# Build your native Android project',
      '$ npx expo run:android',
      '',
      '# Build your native iOS project',
      '$ npx expo run:ios',
    ],
    yarn: [
      '# Build your native Android project',
      '$ yarn expo run:android',
      '',
      '# Build your native iOS project',
      '$ yarn expo run:ios',
    ],
    pnpm: [
      '# Build your native Android project',
      '$ pnpm expo run:android',
      '',
      '# Build your native iOS project',
      '$ pnpm expo run:ios',
    ],
    bun: [
      '# Build your native Android project',
      '$ bun expo run:android',
      '',
      '# Build your native iOS project',
      '$ bun expo run:ios',
    ],
  }}
/>

> Saiba mais sobre [como compilar apps nativos](/more/expo-cli/#compiling).

## Alterações extras \{#extra-changes}

As alterações a seguir são opcionais, mas recomendadas.

**.gitignore**

Você pode adicionar **.expo** ao seu **.gitignore** para evitar que valores gerados pela Expo CLI sejam versionados. Esses [valores são exclusivos do projeto](/more/expo-cli/#expo-directory) no seu computador local.

Os diretórios **android** e **ios** são adicionados automaticamente ao **.gitignore** quando você cria um novo projeto, o que evita que sejam versionados entre um prebuild e outro.

**app.json**

Remova todos os campos que estão fora do objeto `expo` de nível superior, pois eles não serão usados em `npx expo prebuild`.

<DiffBlock
  raw={`diff --git a/app.json b/app.json
index 0000000..1111111 100644
--- a/app.json
+++ b/app.json
@@ -1,4 +1,5 @@
 {
-  "name": "myapp",
-  "displayName": "myapp"
+  "expo": {
+    "name": "myapp"
+  }
 }`}
/>

**metro.config.js**

Veja [Personalizando o Metro](/guides/customizing-metro/).

**package.json**

Vale trocar os scripts pelos comandos de execução da [Expo CLI](/more/expo-cli/#compiling):

<DiffBlock
  raw={`diff --git a/package.json b/package.json
index 0000000..1111111 100644
--- a/package.json
+++ b/package.json
@@ -5,5 +5,5 @@
   "scripts": {
     "start": "expo start",
-    "android": "react-native run-android",
-    "ios": "react-native run-ios",
+    "android": "expo run:android",
+    "ios": "expo run:ios",
   },`}
/>

Esses comandos têm logs melhores, assinatura de código automática, melhor tratamento de simuladores e garantem que você execute `npx expo start` para servir os arquivos.

## Migrar personalizações nativas \{#migrate-native-customizations}

Se o projeto tiver alguma personalização nativa (alterações nos diretórios **android** ou **ios**, como a configuração do ícone do app ou da splash screen), você precisará configurar o app config (**app.json**) para refletir essas alterações.

- Verifique se suas alterações se sobrepõem aos [campos do app config](/versions/latest/config/app/) já existentes. Por exemplo, se você tem um ícone de app, defina-o como `expo.icon` no **app.json** e execute `npx expo prebuild` novamente.
- Veja se algum dos pacotes que você usa exige um [config plugin do Expo][config-plugins]. Se um pacote precisar de alterações adicionais dentro dos diretórios **android** ou **ios**, provavelmente você vai precisar de um config plugin. Alguns plugins podem ser adicionados automaticamente executando `npx expo install` com todos os pacotes das dependências do **package.json**. Se um pacote exigir um plugin, mas não fornecer um, confira os plugins da comunidade em [`expo/config-plugins`](https://github.com/expo/config-plugins) para ver se já existe algum.
- Você pode usar a [extensão Expo para VS Code][vs-code-expo] para inspecionar as alterações e fazer debug caso o prebuild não esteja gerando o código nativo esperado. Basta pressionar <kbd>Cmd ⌘</kbd> + <kbd>Shift</kbd> + <kbd>P</kbd>, digitar "Expo: Preview Modifier" e selecionar o arquivo nativo que você quer inspecionar.
- Além disso, você pode desenvolver config plugins locais para atender às suas necessidades. Veja [como desenvolver um config plugin](/config-plugins/development-and-debugging/#plugin-development).

## Adicionar mais recursos \{#add-more-features}

O prebuild é só a ponta do iceberg da automação. Estes são alguns recursos que você pode adotar em seguida:

- [Expo Build](/build/setup): assinatura de código e build na nuvem.
- [Expo Update](/build/updates): envie updates OTA instantaneamente.
- [Expo para web](/workflow/web): rode seu app no navegador.
- [Expo Dev Client][dev-client]: crie um app próprio no estilo "Expo Go" em torno do seu runtime nativo.
- [API de módulos nativos do Expo][expo-modules-core]: escreva módulos com Swift e Kotlin. Isso é suportado automaticamente ao usar `npx expo prebuild`.
