O [Bun](https://bun.sh/) é um runtime JavaScript e uma alternativa direta ao [Node.js](https://nodejs.org/en). Em projetos Expo, o Bun pode ser usado para instalar pacotes npm e executar scripts Node.js. Os benefícios são uma instalação de pacotes mais rápida do que com npm, pnpm ou Yarn e [pelo menos 4x mais rápido para iniciar em comparação com o Node.js](https://bun.sh/docs#design-goals), o que dá um impulso enorme à sua experiência de desenvolvimento local.

  <Requirement title="Bun instalado na máquina">

## Iniciar um novo projeto Expo com o Bun \{#start-a-new-expo-project-with-bun}

Para criar um novo projeto, execute o comando:

<Terminal cmd={['$ bun create expo-app my-app']} />

Você também pode executar qualquer script do **package.json** com `bun run`:

<Terminal cmd={['$ bun run ios']} />

Para instalar qualquer biblioteca do Expo, use `bun expo install`:

<Terminal cmd={['$ bun expo install expo-audio']} />

## Usar o Bun com o Expo Build \{#use-bun-with-expo-build}

O Expo Build decide qual gerenciador de pacotes usar com base no lockfile do código. Se quiser que o Expo Build use o Bun, execute `bun install` no código. Isso cria um lockfile do Bun: **bun.lock** nas versões 1.2 e mais recentes, ou **bun.lockb** em versões mais antigas. Enquanto um desses lockfiles estiver no código, o Bun será usado como gerenciador de pacotes nos seus builds. Apague qualquer lockfile gerado por outros gerenciadores de pacotes.

### Personalizar a versão do Bun no Expo Build \{#customize-bun-version-on-expo-build}

O Bun vem instalado por padrão no Expo Build. Veja as [imagens de servidor Android](/build-reference/infrastructure/#android-server-images) e as [imagens de servidor iOS](/build-reference/infrastructure/#ios-server-images) para saber qual versão do Bun é usada pela imagem do seu build.

Para usar uma [versão exata do Bun](/eas/json/#bun) com o Expo Build, adicione o número da versão no **eas.json**, na configuração do perfil de build. Por exemplo, a configuração abaixo especifica a versão `1.0.0` do Bun para o perfil de build `development`:

{/* prettier-ignore */}
```json eas.json
{
  "build": {
    "development": {
      /* @info Use `bun` property in eas.json to specify the exact version.*/
      "bun": "1.0.0"
      /* @end */
      /* @hide ... */ /* @end */
    }
    /* @hide ... */ /* @end */
  }
}
```

## Dependências confiáveis \{#trusted-dependencies}

Diferentemente de outros gerenciadores de pacotes, o Bun não executa automaticamente os scripts de ciclo de vida das bibliotecas instaladas, porque isso é considerado um risco de segurança. No entanto, se um pacote que você está instalando tiver um script `postinstall` que precisa rodar, você deve declarar isso explicitamente, incluindo essa biblioteca no array [`trustedDependencies`](https://bun.sh/guides/install/trusted) do seu **package.json**.

Por exemplo, se você instalar `packageA`, que depende de `packageB`, e `packageB` tiver um script `postinstall`, você precisa adicionar `packageB` em `trustedDependencies`.

Para adicionar uma dependência confiável no **package.json**, inclua:

```json package.json
"trustedDependencies": ["your-dependency"]
```

Depois, remova o lockfile e reinstale as dependências:

<Terminal
  cmd={['$ rm -rf node_modules', '$ rm bun.lock bun.lockb', '$ bun install']}
  cmdCopy="rm -rf node_modules && rm bun.lock bun.lockb && bun install"
/>

## Erros comuns \{#common-errors}

### O Expo Build falha ao usar Sentry e Bun \{#expo-build-fails-when-using-sentry-and-bun}

Se você usa `sentry-expo` ou `@sentry/react-native`, esses pacotes dependem do `@sentry/cli`, que atualiza os source maps no Sentry durante o build. O pacote `@sentry/cli` tem um script `postinstall` que precisa ser executado para que o script de "upload source maps" fique disponível.

Para resolver, adicione `@sentry/cli` ao array de [dependências confiáveis](#trusted-dependencies) no **package.json**:

```json package.json
"trustedDependencies": ["@sentry/cli"]
```

### O Expo Build falha com incompatibilidade de runtime version ao usar dependências com patch \{#expo-build-fails-with-a-runtime-version-mismatch-when-using-patched-dependencies}

Quando o Bun instala um pacote que tem um patch em [`patchedDependencies`](https://bun.sh/docs/pm/cli/patch), ele grava um arquivo de tag vazio chamado **.bun-tag-&lt;hash&gt;** no diretório do pacote. O nome do arquivo de tag depende da versão do Bun, então duas versões diferentes do Bun gravam nomes diferentes para o mesmo patch.

A [fingerprint](/versions/latest/sdk/fingerprint/) inclui o arquivo de tag quando o pacote com patch é um módulo nativo ou um config plugin, no SDK 57 e anteriores, ou com o `strict` [preset](/versions/latest/sdk/fingerprint/#fingerprintpreset) no SDK 58 e posteriores. Se a fingerprint incluir o arquivo de tag e o Expo Build usar uma versão do Bun diferente da sua máquina, as duas fingerprints serão diferentes. Com a [política de runtime version](/versions/latest/sdk/updates/#automatic-configuration-using-runtime-version-policies) `fingerprint`, o build então falha na fase **Configure expo-updates** com este erro:

```text
Runtime version calculated on local machine not equal to runtime version calculated during build.
```

Para resolver, adicione os arquivos de tag ao **.fingerprintignore** na raiz do projeto:

```ignore .fingerprintignore
**/node_modules/**/.bun-tag-*
```

O `**/` inicial também corresponde a arquivos de tag em um diretório **node_modules** pai, como na raiz de um monorepo. Você também pode [usar a mesma versão do Bun no Expo Build](/eas/json/#bun) que na sua máquina.
