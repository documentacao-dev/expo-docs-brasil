O termo "local-first" foi usado pela primeira vez no artigo ["Local-first software"](https://www.inkandswitch.com/local-first/), escrito pelo laboratório de pesquisa [Ink & Switch](https://www.inkandswitch.com/), mas as ideias por trás dele existem há muito tempo. É a arquitetura que sustenta apps bem conhecidos, como [Linear](https://linear.app/), [Superhuman](https://superhuman.com/), [Excalidraw](https://excalidraw.com/) e até o [Apple Notes](<https://en.wikipedia.org/wiki/Notes_(Apple)>).

No software local-first, "a disponibilidade de outro computador nunca deve impedir você de trabalhar" ([via Martin Kleppmann](https://www.youtube.com/watch?v=NMq0vncHJvU)). Quando você está offline, ainda pode ler e escrever diretamente em um banco de dados no seu dispositivo. Você pode confiar que o software funciona offline e sabe que, quando estiver conectado à internet, os seus dados serão sincronizados sem interrupções e estarão disponíveis em qualquer um dos seus dispositivos que execute o app. Quando você está online, essa arquitetura é bastante adequada para apps "multiplayer", [como popularizado pelo Figma](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/).

Para entender melhor o que é local-first e como ele funciona, consulte os [recursos adicionais](#additional-resources) abaixo.

## Por que usar a arquitetura local-first? \{#why-use-local-first-architecture}

### Benefícios para a experiência do usuário \{#user-experience-benefits}

Software local-first parece **rápido** porque as interações não dependem mais da rede. Você pode ler e escrever diretamente em um banco de dados no seu dispositivo.

Você pode confiar que o software funciona offline e sabe que, quando estiver conectado à internet, os seus dados serão sincronizados sem interrupções e estarão disponíveis em qualquer dispositivo que execute o app.

Outra característica do software local-first é que ele é colaborativo: vários dispositivos podem trabalhar nos mesmos dados, e as mudanças são sincronizadas entre todos eles. Isso pode acontecer em tempo real, quando você colabora em um design no [Figma](https://www.figma.com/), ou de forma assíncrona, quando cria uma tarefa offline no Linear e ela é sincronizada assim que você volta a ficar online.

### Benefícios para a experiência do desenvolvedor \{#developer-experience-benefits}

Você não precisa mais gerenciar os vários estados do app para cada requisição de rede, como "carregado", "carregando", "erro" e assim por diante, com os respectivos estados de UI e outras lógicas. Escreva em um banco de dados local, e o app sincronizará automaticamente as mudanças com o servidor. Assim, você pode focar em construir o app e se preocupar menos com a rede e com os estados offline.

A arquitetura local-first não elimina todos os estados que dependem da rede. Algumas ações, como enviar um e-mail, só são concluídas quando um serviço remoto as aceita. Grave essas ações no banco de dados local primeiro. Depois, acompanhe o estado delas, como "na fila", "enviando", "aceita" e "falhou".

A disponibilidade do seu servidor ainda pode ser importante, mas, em caso de indisponibilidade, os seus usuários continuam conseguindo acessar o app e trabalhar. Você pode até oferecer um mecanismo para sincronizar os dados sem passar pelo seu servidor.

## Desafios na criação de apps local-first \{#challenges-in-building-local-first-apps}

As ferramentas disponíveis hoje ainda estão em estágio inicial, então você pode acabar resolvendo problemas que esperaria que as ferramentas atuais já resolvessem. Por exemplo, pode ser necessário implementar uma camada de sincronização personalizada ou descobrir como lidar com permissões para vários usuários operando sobre os mesmos dados. À medida que o ecossistema evolui, esperamos que criar apps local-first fique mais fácil. Se você não estiver preparado para ser um dos primeiros a adotar essa tecnologia, com tudo o que isso implica, talvez seja melhor esperar que as ferramentas amadureçam antes de começar a construir o seu app com elas.

## Ferramentas para criar apps local-first \{#tools-for-building-local-first-apps}

Uma lista completa de ferramentas está disponível no [site da comunidade "Local-first software"](https://localfirstweb.dev/). A seguir, há uma lista mais curta das ferramentas que nós, da Expo, já usamos diretamente.

Uma forma de pensar nas ferramentas local-first é agrupá-las nas seguintes categorias: persistência, gerenciamento de estado e sincronização. Algumas ferramentas se encaixam em mais de uma categoria, se lidam com vários aspectos do problema. A sincronização pode ser dividida ainda em estruturas de dados sincronizáveis e camadas de transporte.

### Legend-State \{#legend-state}

[Legend-State](https://legendapp.com/open-source/state/v3/) é uma biblioteca de estado e sincronização extremamente rápida e completa, que permite escrever menos código para criar apps mais rápidos. Ela tem os seguintes objetivos principais:

- Gerenciamento de estado mais rápido para apps React
- Reatividade granular para renderizações mínimas
- Sincronização e persistência avançadas (com suporte nativo ao Supabase)

Ela funciona com o Expo e o React Native (por meio do [`react-native-async-storage`](https://github.com/react-native-async-storage/async-storage?tab=readme-ov-file#react-native-async-storage)). Isso a torna uma combinação perfeita para criar apps mobile e web local-first. Comece usando o [exemplo Legend-State com Supabase](https://github.com/expo/examples/tree/master/with-legend-state-supabase):

<Terminal cmd={['$ npx create-expo-app --example with-legend-state-supabase']} />

### TinyBase \{#tinybase}

[TinyBase](https://tinybase.org/) se apresenta como "o armazenamento de dados reativo para apps local-first". Trata-se de uma biblioteca de gerenciamento de estado que se conecta a muitas das camadas de sincronização e persistência mais populares, como [Yjs](#yjs) e [SQLite](#sqlite). É uma ótima escolha para criar apps local-first que precisam persistir e sincronizar dados. Comece usando o [exemplo do TinyBase](https://github.com/expo/examples/tree/master/with-tinybase):

<Terminal cmd={['$ npx create-expo-app --example with-tinybase']} />

O TinyBase funciona perfeitamente com o Expo Go, o que permite desenvolver rapidamente. No Android e no iOS, ele usa a biblioteca [`expo-sqlite`](/versions/latest/sdk/sqlite/) para persistir os dados. Na web, ele usa a API [`localStorage`](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage). [Beto Moedano](https://github.com/betomoedano) mostra como criar uma [lista de compras universal e local-first](https://github.com/betomoedano/groceries-shopping-list-app) no vídeo a seguir:

### SQLite \{#sqlite}

[Expo SQLite](/versions/latest/sdk/sqlite/) é uma biblioteca SQLite que é uma ótima escolha para persistência em apps local-first. Você pode usar o SQLite com diferentes camadas de gerenciamento de estado e sincronização na frente dele, como o [`y-expo-sqlite`](https://github.com/brentvatne/y-expo-sqlite) para persistir documentos do [Yjs](#yjs), e o [TinyBase](#tinybase) como camada de gerenciamento de estado. Usar o SQLite é flexível, mas você precisará combiná-lo com outras ferramentas, ou criar as suas próprias, para obter uma solução local-first completa. Veja a [referência da API do Expo SQLite](/versions/latest/sdk/sqlite/) para mais informações.

### Yjs \{#yjs}

[Yjs](https://github.com/yjs/yjs) é uma [implementação de CRDT](https://github.com/yjs/yjs?tab=readme-ov-file#yjs-crdt-algorithm) que fornece tipos de dados que podem ser sincronizados entre vários clientes. Ao criar um app com o Yjs e trabalhar com dados que você quer poder sincronizar, então use `Y.Array` e `Y.Map` para representar esses dados, em vez de `Array` e `Object`. Você pode usar uma biblioteca como o [TinyBase](#tinybase) para o gerenciamento de estado sobre o Yjs. A persistência pode ser feita por diversas ferramentas, desde um arquivo JSON no sistema de arquivos até um banco de dados completo (como o [`y-expo-sqlite`](https://github.com/brentvatne/y-expo-sqlite)), e tudo o que existe entre eles. Veja o [repositório do Yjs no GitHub](https://github.com/yjs/yjs) para mais informações.

### Prisma \{#prisma}

O [Prisma](https://prisma.io) é conhecido como o ORM mais popular para backends Node.js e TypeScript, e agora está [disponível para Expo e React Native em acesso antecipado](https://www.prisma.io/blog/bringing-prisma-orm-to-react-native-and-expo). O Prisma tem como objetivo oferecer uma solução local-first completa, com gerenciamento de estado, sincronização e persistência cobertos para você. Embora ainda esteja no começo, [Beto Moedano](https://github.com/betomoedano) preparou um tutorial completo de uso do Prisma com o Expo para criar um clone local-first do Notion. [Confira o código no GitHub](https://github.com/betomoedano/React-Native-Notion-Clone).

### Jazz \{#jazz}

[Jazz](https://jazz.tools/) é um banco de dados relacional local-first com sincronização em tempo real, suporte offline e permissões em nível de linha. Ele é open source, oferece suporte de primeira classe ao Expo e ao React Native, e você pode [hospedá-lo por conta própria](https://jazz.tools/docs/getting-started/server-setup) para começar rapidamente. Para saber mais, confira os [exemplos](https://github.com/garden-co/jazz/tree/main/examples) ou veja o [guia de primeiros passos](https://jazz.tools/docs/install/client) com instruções detalhadas.

### LiveStore \{#livestore}

[LiveStore](https://docs.livestore.dev/getting-started/expo/) é uma camada de dados local-first centrada no cliente, para apps de alto desempenho. Ela oferece suporte de primeira classe ao Expo e é uma ótima escolha para criar apps local-first. Veja o post no blog sobre [LiveStore: camada de dados baseada em SQLite para apps local-first](https://expo.dev/blog/local-first-application-development-with-livestore).

### Turso \{#turso}

[Turso](https://turso.tech) é um serviço de banco de dados moderno construído sobre o SQLite. Ele agora oferece [Offline Sync](https://turso.tech/blog/turso-offline-sync-public-beta), que possibilita experiências verdadeiramente local-first. Você pode sincronizar bancos de dados entre fontes locais e remotas, com sincronização bidirecional e detecção de conflitos integrada. Embora a resolução automática de conflitos ainda não esteja disponível, esse recurso já é um grande avanço. Você pode usar o Turso hoje com o [expo-sqlite](/versions/latest/sdk/sqlite). Para saber mais, leia o post do blog [Turso: Offline Sync Public Beta](https://turso.tech/blog/turso-offline-sync-public-beta). Para um exemplo de integração, confira o [Notes App](https://github.com/betomoedano/notes-app).

### RxDB \{#rxdb}

[RxDB](https://rxdb.info/) (Reactive Database) é um banco de dados NoSQL local-first para apps JavaScript. Ele é altamente reativo, permitindo que você se inscreva nos resultados de consultas para que a interface seja atualizada automaticamente quando os dados mudarem. O RxDB foca em recursos offline-first para criar apps que funcionam mesmo sem internet e que sincronizam quando voltam a ficar online. O RxDB funciona com o Expo usando o [adaptador de armazenamento SQLite](https://rxdb.info/rx-storage-sqlite.html#usage-with-expo-sqlite), que encapsula o [`expo-sqlite`](/versions/latest/sdk/sqlite/). Ele também oferece vários plugins de replicação para sincronizar com o seu backend existente, seja ele HTTP, GraphQL, Supabase ou um backend personalizado.
