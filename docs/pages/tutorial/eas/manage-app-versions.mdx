## Como funcionam as versões do app voltadas ao desenvolvedor e ao usuário \{#understanding-developer-facing-and-user-facing-app-versions}

A versão de um app é composta por dois valores:

- Valor voltado ao desenvolvedor: representado pelo [`versionCode`](/versions/latest/config/app/#versioncode) no Android e pelo [`buildNumber`](/versions/latest/config/app/#buildnumber) no iOS.
- Valor voltado ao usuário: representado pela [`version`](/versions/latest/config/app/#version) na [configuração do app](/workflow/configuration/).

Tanto a Google Play Store quanto a Apple App Store usam os valores voltados ao desenvolvedor para identificar cada build único. Por exemplo, se enviarmos um app com a versão `1.0.0 (1)` (que é a combinação dos valores voltados ao usuário e ao desenvolvedor), não podemos enviar outro build às lojas com a mesma versão do app. Enviar builds com números de versão duplicados faz o envio falhar.

Um exemplo de como gerenciar manualmente os valores voltados ao desenvolvedor aparece abaixo, em `android.versionCode` e `ios.buildNumber` no **app.config.js**. **Não precisamos adicionar nem gerenciar esses valores manualmente, porque o Expo Build automatiza isso para nós**.

```js app.config.js
{
  ios: {
    buildNumber: 1
    /* @hide ... */ /* @end */
  },
  android: {
    versionCode: 1
  }
  /* @hide ... */ /* @end */
}
```

> **info** O Expo Build não cuida do [número de versão voltado ao usuário](/build-reference/app-versions/#user-facing-version). Em vez disso, atualizamos a propriedade `version` na configuração do app antes de criar um build de produção.

## Gerenciamento automático de versões do app com o Expo Build \{#automatic-app-version-management-with-expo-build}

Por padrão, o Expo Build ajuda a automatizar os valores voltados ao desenvolvedor. Ele usa a [fonte de versão remota](/build-reference/app-versions/#remote-version-source) para incrementar automaticamente esses valores sempre que uma nova versão de produção é criada.

Quando configuramos o projeto com o comando `eas build:configure`, a EAS CLI adicionou automaticamente as seguintes propriedades no **eas.json**:

- `cli.appVersionSource`, definida como `remote`
- [`build.production.autoIncrement`](/eas/json/#autoincrement-1), definida como `true`

Você pode vê-las no **eas.json** do projeto:

{/* prettier-ignore */}
```json eas.json
{
  "cli": {
    /* @hide ... */ /* @end */
    /* @info The `appVersionSource` is set to `remote`. */
    "appVersionSource": "remote"
    /* @end */
  },
  "build": {
    "production": {
      /* @info The `autoIncrement` is set `true` to automatically increment the `versionCode` or `buildNumber`. */
      "autoIncrement": true
      /* @end */
    }
  }
  /* @hide ... */ /* @end */
}
```

Quando criarmos um novo build de produção nos dois próximos capítulos, o `versionCode` no Android e o `buildNumber` no iOS vão ser incrementados automaticamente.

<Collapsible summary="Sincronizando as versões voltadas ao desenvolvedor de apps já publicados no Expo Services">

Se o seu app já está publicado nas lojas, as versões voltadas ao desenvolvedor já estão definidas. Ao migrar esse app para usar o Expo Build, siga os passos abaixo para sincronizar essas versões:

- Na janela do terminal, rode o comando `eas build:version:set`:

<Terminal cmd={['$ eas build:version:set']} />

- Selecione a plataforma (Android ou iOS) quando solicitado.
- Quando aparecer a pergunta **Do you want to set app version source to remote now?**, selecione **yes**. Isso vai definir `cli.appVersionSource` como `remote` no **eas.json**.
- Quando aparecer a pergunta **What version would you like to initialize it with?**, digite o último número de versão que você definiu nas lojas de apps.

Depois desses passos, as versões do app vão estar sincronizadas remotamente com o Expo Build. Você pode definir `build.production.autoIncrement` como `true` no **eas.json**. A partir daí, quando você criar um novo build de produção, o `versionCode` e o `buildNumber` serão incrementados automaticamente.

</Collapsible>
