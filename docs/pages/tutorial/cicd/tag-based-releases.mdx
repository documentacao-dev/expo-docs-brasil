Fazer push para uma branch de release roda o workflow de produção a cada commit, até nos que nunca tivemos a intenção de publicar como release.

## O que você vai aprender

- Trocar o trigger do workflow de produção, de uma branch `release/*`, para uma tag do Git que corresponda a `v*.*.*`
- Criar um release fazendo push de uma tag a partir da `main` e acompanhar a execução do workflow no dashboard da Expo
- Excluir tags de pré-lançamento, como `v1.0.0-rc.1`, da produção e rodar release candidates em um workflow separado

## Tags como eventos de release

O Expo Workflows oferece suporte a triggers baseados em tags pelo [`on.push`](/eas/workflows/syntax/#onpush), com uma lista `tags`. O workflow só roda quando uma tag que corresponde a um padrão glob é enviada para o remoto. Uma tag do Git é um evento único, ligado a um commit e a uma versão específicos, diferentemente de uma branch, que pode ser atualizada com o tempo. Por isso, tags são ótimas para marcar releases.

Um workflow de release baseado em tags serve bem para times que:

- Querem que o número da versão no Git seja o mesmo que a versão enviada aos usuários do app
- Publicam direto a partir da `main`, sem manter branches de release de longa duração
- Querem um histórico claro de cada commit de release, por versão

## Troque o production.yml para um trigger de tag

Abra o workflow **.eas/workflows/production.yml** do [capítulo anterior](/tutorial/cicd/production/) e substitua o trigger `on.push.branches` por `on.push.tags`. O restante do workflow continua igual.

<Step label="1">

### Troque o trigger

Substitua o trigger `branches` por um trigger `tags`. O glob `tags` corresponde a tags como `v1.0.0`, `v2.3.7` e `v10.0.0-beta.1`.

```yaml .eas/workflows/production.yml
name: Deploy to production

# @info #
on:
  push:
    tags: ['v*.*.*']
# @end #

jobs:
  fingerprint:
    name: Fingerprint
    type: fingerprint
    environment: production
  get_android_build:
    name: Check for existing Android build
    needs: [fingerprint]
    type: get-build
    params:
      fingerprint_hash: ${{ needs.fingerprint.outputs.android_fingerprint_hash }}
      profile: production
  get_ios_build:
    name: Check for existing iOS build
    needs: [fingerprint]
    type: get-build
    params:
      fingerprint_hash: ${{ needs.fingerprint.outputs.ios_fingerprint_hash }}
      profile: production
  build_android:
    name: Build Android
    needs: [get_android_build]
    if: ${{ !needs.get_android_build.outputs.build_id }}
    type: build
    params:
      platform: android
      profile: production
  build_ios:
    name: Build iOS
    needs: [get_ios_build]
    if: ${{ !needs.get_ios_build.outputs.build_id }}
    type: build
    params:
      platform: ios
      profile: production
  update_android:
    name: Publish Android update
    needs: [get_android_build]
    if: ${{ needs.get_android_build.outputs.build_id }}
    type: update
    params:
      branch: production
      platform: android
  update_ios:
    name: Publish iOS update
    needs: [get_ios_build]
    if: ${{ needs.get_ios_build.outputs.build_id }}
    type: update
    params:
      branch: production
      platform: ios
```

Para que as tags disparem o workflow, precisamos escolher um padrão que combine com o fluxo do nosso time. Padrões comuns incluem:

- `['v*']` corresponde a qualquer tag que comece com `v`
- `['v*.*.*']` corresponde a versões semânticas estritas, com três partes (recomendado)

Não precisamos mudar nenhum outro job. Os jobs `fingerprint`, `get-build`, `build` e `update` funcionam do mesmo jeito, porque operam sobre o commit.

</Step>

<Step label="2">

### Faça commit e push da mudança do workflow

Faça commit da mudança no **production.yml** e envie para a `main`. Isso não dispara o workflow, porque trocamos um trigger de branch por um trigger de tag.

<Terminal
  cmd={[
    '$ git add .eas/workflows/production.yml',
    '',
    '$ git commit -m "Switch production workflow to tag trigger"',
    '',
    '$ git push origin main',
  ]}
  cmdCopy="git add .eas/workflows/production.yml && git commit -m 'Switch production workflow to tag trigger' && git push origin main"
/>

</Step>

<Step label="3">

### Crie uma tag para testar o workflow

Para rodar o workflow, precisamos enviar uma tag que corresponda ao padrão glob definido no **production.yml**.

Faça uma mudança em TypeScript/JavaScript no nosso projeto de exemplo, faça commit dela e envie uma nova tag:

<Terminal
  cmd={[
    '$ git add .',
    '',
    '$ git commit -m "Fix welcome copy"',
    '',
    '$ git tag v0.1.0',
    '',
    '$ git push origin main --tags',
  ]}
  cmdCopy="git add . && git commit -m 'Fix welcome copy' && git tag v0.1.0 && git push origin main --tags"
/>

O workflow é disparado pela tag `v0.1.0`. Abra o dashboard da Expo e, em **Workflows**, veja "Deploy to production" rodando com `refs/tags/v0.1.0` como sua branch:

## Tags de pré-lançamento para release candidates

O glob `v*.*.*` também corresponde a tags de pré-lançamento, como `v1.0.0-rc.1`, que enviariam um release candidate aos usuários do app. Para manter os release candidates fora da produção, exclua-os do trigger do workflow de produção:

```yaml .eas/workflows/production.yml
on:
  push:
    tags: ['v*.*.*', '!v*.*.*-rc.*']
```

Para testar um release candidate antes do lançamento de verdade, crie um workflow separado que corresponda só a tags de pré-lançamento (`tags: ['v*.*.*-rc.*']`) e reutilize os jobs `fingerprint`, `get-build` e `build`, sem os jobs `update` e `submit`. O mesmo pipeline roda, e nada chega aos usuários do app.
