Refazer manualmente o development client a cada push para um repositório do GitHub pode ser lento. Membros do time ou novos colaboradores que puxam mudanças nativas (um novo módulo, uma nova permissão, um upgrade de SDK) precisam esperar por um build novo antes de conseguir rodar o projeto.

Automatizar development builds na branch `main` mantém um build atualizado pronto para instalar. Podemos rodar `eas build:dev` para instalar o build compatível mais recente. Se o fingerprint do projeto bater com um build existente, o comando baixa esse build em vez de criar um novo.

## O que você vai aprender \{#learning-outcomes}

- Automatizar [development builds](/develop/development-builds/introduction/) para Android e iOS com o tipo de job `build`
- Usar os jobs `fingerprint` e `get-build` para pular o rebuild quando o código nativo não mudou
- Adicionar um job customizado de testes unitários que bloqueia o workflow enquanto os testes não passarem

<Prerequisites>

<Requirement title="Expo Build configurado para development">

A EAS CLI pede para gerar as credenciais na primeira vez que disparamos um build para um perfil. Dispare o development build manualmente para Android e iOS para que as credenciais existam antes de o workflow rodar:

<Terminal cmd={['$ eas build --profile development --platform all']} />

</Requirement>

</Prerequisites>

## O job `build` para development builds \{#the-build-job-type-for-development-builds}

O tipo de job `build` é um dos [jobs pré-empacotados](/tutorial/cicd/first-workflow/#types-of-jobs-in-expo-workflows) do Expo Workflows. Em vez de definir cada etapa do processo de build, usamos o job `build` para rodar um Expo Build para Android e iOS.

Neste capítulo, usamos o perfil de build `development` do nosso **eas.json**. Usamos esse perfil durante o desenvolvimento do app com Expo.

<Step label="1">

### Adicione um build.yml \{#add-a-buildyml}

Dentro de **.eas/workflows/**, adicione um novo arquivo chamado **build.yml**. Ele usa o job `build` com os parâmetros `profile` e `platform` para criar development builds para Android e iOS.

Adicione o código a seguir ao arquivo **build.yml**:

```yaml .eas/workflows/build.yml
name: Development builds

jobs:
  build_android:
    name: Build Android
    type: build
    params:
      platform: android
      profile: development
  build_ios:
    name: Build iOS
    type: build
    params:
      platform: ios
      profile: development
```

Adicionamos dois jobs: `build_android` e `build_ios`. Ambos são do tipo `build`, com parâmetros diferentes de plataforma e de perfil de build.

A chave `params` de cada job inclui:

- [`platform`](/eas/workflows/pre-packaged-jobs/#build) define o SO de destino do build (`android` ou `ios`)
- [`profile`](/build/eas-json/#build-profiles) especifica o perfil de build do nosso **eas.json**

</Step>

<Step label="2">

### Rode o workflow manualmente \{#run-the-workflow-manually}

Vamos rodar o workflow manualmente com o comando:

<Terminal cmd={['$ eas workflow:run .eas/workflows/build.yml']} />

</Step>

<Step label="3">

### Verifique no dashboard da Expo \{#verify-on-the-expo-dashboard}

No dashboard da Expo, veja que aparece "Triggered manually" na aba **Workflow graph**. Sempre que o **Trigger** mostrar **Manual**, significa que o workflow foi iniciado com o comando `eas workflow:run`.

<ContentSpotlight

  src="/static/images/tutorial/cicd/eas-workflows-development-build-manual-run.png"
  className="max-w-160"
/>

Os logs de cada build aparecem dentro da interface do workflow. Clique no ID de um build para abrir a página dele no Expo Build.

<ContentSpotlight
  alt="Página de detalhes do Expo Build de um development build para Android, mostrando o status do build, o hash do fingerprint, o SHA do commit e a saída de log expandida."
  src="/static/images/tutorial/cicd/eas-build-android-development-build-logs.webp"
  className="max-w-160"

> **important** Jobs sem dependências rodam em paralelo por padrão no Expo Workflows. No workflow acima, como os jobs `build_android` e `build_ios` não têm dependências, eles começam ao mesmo tempo.

Espere os dois builds terminarem antes de ir para o próximo passo. Quando terminarem, podemos usar os botões **Install** ou **Open with [Orbit](/build/orbit/)**, ou baixar pelo **Artifacts** para instalar no dispositivo, emulador ou simulador.

</Step>

## Pule builds desnecessários com fingerprints \{#skip-unnecessary-builds-with-fingerprints}

Quando o projeto tem só mudanças em TypeScript/JavaScript, o development build existente continua compatível, então não precisamos de um novo.

[**Expo Fingerprint**](/versions/latest/sdk/fingerprint/) automatiza essa decisão. Ele gera um hash das características nativas do projeto (dependências, arquivos do projeto nativo, configuração). Se o hash bater com um build existente, o código nativo não mudou e o Expo Workflows pula o rebuild. Se o hash for diferente, o código nativo mudou e o Expo Workflows cria um novo build.

<FingerprintFlow />

Vamos atualizar o **build.yml** passo a passo para detectar mudanças nativas e fazer o build só quando for necessário.

<Step label="1">

### Adicione um job de fingerprint \{#add-a-fingerprint-job}

O job pré-empacotado [`fingerprint`](/eas/workflows/pre-packaged-jobs/#fingerprint) gera um hash das características nativas do projeto e produz um hash de fingerprint para cada plataforma. O campo `environment` diz ao Expo Workflows qual [configuração de variáveis de ambiente](/eas/environment-variables/) usar. `environment` e `profile` podem ter o mesmo nome, mas se referem a coisas diferentes. `profile` aponta para um perfil de build no **eas.json** (como fazer o build). `environment` aponta para variáveis de ambiente configuradas no Expo Services (quais valores injetar no momento do build).

Atualize o **build.yml** para adicionar o job `fingerprint` antes dos jobs de build:

```yaml .eas/workflows/build.yml
name: Development builds

jobs:
  # @info #
  fingerprint:
    name: Fingerprint
    type: fingerprint
    environment: development
  # @end #
  build_android:
    # ...
  build_ios:
    # ...
```

O job `fingerprint` produz duas saídas: `android_fingerprint_hash` e `ios_fingerprint_hash`. Usamos esses hashes na próxima etapa para verificar se já existe um build compatível.

</Step>

<Step label="2">

### Adicione jobs get-build \{#add-get-build-jobs}

O job pré-empacotado [`get-build`](/eas/workflows/pre-packaged-jobs/#get-build) verifica se já existe um build para um determinado hash de fingerprint e perfil. Se houver um build correspondente, ele produz um `build_id`. Se não houver, o `build_id` fica vazio.

No arquivo do workflow, vamos adicionar os jobs `get_android_build` e `get_ios_build` entre `fingerprint` e os jobs de build. Cada um usa `needs: [fingerprint]` para esperar o job de fingerprint terminar e acessar a saída dele:

```yaml .eas/workflows/build.yml
name: Development builds

jobs:
  fingerprint:
    # ...
  # @info #
  get_android_build:
    name: Check for existing Android build
    needs: [fingerprint]
    type: get-build
    params:
      fingerprint_hash: ${{ needs.fingerprint.outputs.android_fingerprint_hash }}
      profile: development
  get_ios_build:
    name: Check for existing iOS build
    needs: [fingerprint]
    type: get-build
    params:
      fingerprint_hash: ${{ needs.fingerprint.outputs.ios_fingerprint_hash }}
      profile: development
  # @end #
  build_android:
    # ...
  build_ios:
    # ...
```

No workflow acima, os jobs `get-build` recebem o hash de fingerprint do job anterior usando a sintaxe de expressão `${{ needs.fingerprint.outputs.* }}`.

</Step>

<Step label="3">

### Adicione builds condicionais \{#add-conditional-builds}

O campo [`if`](/eas/workflows/syntax/#jobsjob_idif) controla se um job roda. A expressão `${{ !needs.get_android_build.outputs.build_id }}` significa: _rode um job somente se o `get-build` não encontrou um build correspondente_. O `!` é o operador de negação. Se já existir um build compatível para este fingerprint, o job de build é pulado.

Vamos atualizar cada job de build para depender do seu job `get-build` e adicionar a condição `if`:

```yaml .eas/workflows/build.yml
name: Development builds

jobs:
  fingerprint:
    # ...
  get_android_build:
    # ...
  get_ios_build:
    # ...
  build_android:
    name: Build Android
    # @info #
    needs: [get_android_build]
    if: ${{ !needs.get_android_build.outputs.build_id }}
    # @end #
    type: build
    params:
      platform: android
      profile: development
  build_ios:
    name: Build iOS
    # @info #
    needs: [get_ios_build]
    if: ${{ !needs.get_ios_build.outputs.build_id }}
    # @end #
    type: build
    params:
      platform: ios
      profile: development
```

</Step>

<Step label="4">

### Adicione um trigger e rode o workflow \{#add-a-trigger-and-run-the-workflow}

Vamos adicionar o trigger `on.push` ao workflow para que ele rode automaticamente a cada push na `main`:

```yaml .eas/workflows/build.yml
name: Development builds

# @info #
on:
  push:
    branches: ['main']
# @end #

jobs:
  fingerprint:
    name: Fingerprint
    type: fingerprint
    environment: development
  get_android_build:
    name: Check for existing Android build
    needs: [fingerprint]
    type: get-build
    params:
      fingerprint_hash: ${{ needs.fingerprint.outputs.android_fingerprint_hash }}
      profile: development
  get_ios_build:
    name: Check for existing iOS build
    needs: [fingerprint]
    type: get-build
    params:
      fingerprint_hash: ${{ needs.fingerprint.outputs.ios_fingerprint_hash }}
      profile: development
  build_android:
    name: Build Android
    needs: [get_android_build]
    if: ${{ !needs.get_android_build.outputs.build_id }}
    type: build
    params:
      platform: android
      profile: development
  build_ios:
    name: Build iOS
    needs: [get_ios_build]
    if: ${{ !needs.get_ios_build.outputs.build_id }}
    type: build
    params:
      platform: ios
      profile: development
```

Vamos supor que fizemos algumas mudanças em TypeScript/JavaScript no nosso projeto Expo, como trocar a cor de um botão ou atualizar o texto de uma tela. Depois disso, podemos fazer push de um commit para a branch `main` para disparar o workflow a partir do nosso repositório do GitHub:

<Terminal
  cmd={[
    '$ git add .',
    '$ git commit -m "Update button label and tweak styling"',
    '$ git push origin main',
  ]}
  cmdCopy="git add . && git commit -m 'Update button label and tweak styling' && git push origin main"
/>

Isso dispara um novo workflow que termina em segundos. No dashboard da Expo, os builds de Android e iOS são pulados porque já existe um build correspondente da seção anterior.

<ContentSpotlight
  alt="Execução do Expo Workflows em que os jobs de fingerprint e get-build pulam os jobs de build de Android e iOS porque foram encontrados builds existentes compatíveis."
  src="/static/images/tutorial/cicd/eas-workflows-fingerprint-skips-existing-build.png"
  className="max-w-160"
/>

Puxamos as últimas mudanças da branch `main` e rodamos `npx expo start`. O development build existente usa as mudanças de JS.

</Step>

## Jobs customizados para testes unitários \{#custom-jobs-for-unit-testing}

> **info** Esta seção assume que o Jest está configurado no projeto. Para instruções de configuração, veja [Testes unitários com Jest](/develop/unit-testing/).

Quando trabalhamos em equipe, queremos que toda mudança enviada para a branch `main` passe nos testes antes de disparar um novo build.

Sem automação, o time precisa lembrar de rodar os testes localmente antes de fazer push para a `main`. Se alguém esquecer e o código tiver um teste falhando, o próximo workflow pode criar um build com código quebrado.

Com o **Expo Workflows**, podemos automatizar isso combinando um job customizado com os jobs pré-empacotados que já usamos. Esse job customizado roda antes dos jobs de fingerprint e de build. Se um teste falhar, o Expo Workflows interrompe o workflow e não cria nenhum build.

<UnitTestGate />

<Step label="1">

### Adicione um job customizado para os testes unitários \{#add-a-custom-job-for-unit-tests}

No arquivo de workflow **build.yml**, vamos adicionar um job customizado que roda os testes unitários antes de os builds começarem:

```yaml .eas/workflows/build.yml
name: Development builds

on:
  push:
    branches: ['main']

jobs:
  # @info #
  run_tests:
    name: Run unit tests
    steps:
      - uses: eas/checkout # Check out the repo
      - uses: eas/install_node_modules
      - run: npx jest --ci
  # @end #
  fingerprint:
    name: Fingerprint
    # @info Add this to the fingerprint job. It runs only after tests pass; if tests fail, nothing builds. #
    needs: [run_tests]
    # @end #
    type: fingerprint
    environment: development
  get_android_build:
    # ...
  get_ios_build:
    # ...
  build_android:
    # ...
  build_ios:
    # ...
```

O job customizado `run_tests` faz o seguinte:

- `uses: eas/checkout` faz o checkout dos arquivos-fonte do projeto a partir do repositório do GitHub. Jobs customizados rodam em uma máquina virtual nova, então o código não fica disponível por padrão. Este passo é obrigatório antes de acessar qualquer arquivo do projeto.
- `uses: eas/install_node_modules` instala as dependências usando o gerenciador de pacotes detectado no projeto (bun, npm, pnpm ou Yarn). Isso é necessário antes de rodar qualquer comando que dependa de pacotes da pasta **node_modules**, como o Jest.
- `run: npx jest --ci` executa a suíte de testes. A chave `run` roda qualquer comando de shell, parecido com o comando `echo`. A flag `--ci` diz ao Jest para rodar em modo CI, que não observa mudanças nos arquivos e encerra depois de rodar todos os testes.

Agora, o job `fingerprint` tem `needs: [run_tests]`, então ele só roda depois que os testes passam. Se os testes falharem, o Expo Workflows pula o restante do workflow.

</Step>

<Step label="2">

### Dispare o workflow \{#trigger-the-workflow}

Faça commit e push do workflow atualizado junto com o arquivo de teste para a `main`:

<Terminal
  cmd={[
    '$ git add .',
    '$ git commit -m "Add unit tests to development builds workflow"',
    '$ git push origin main',
  ]}
  cmdCopy="git add . && git commit -m 'Add unit tests to development builds workflow' && git push origin main"
/>

Depois de disparar o workflow, abra o dashboard da Expo e observe o fluxo dos jobs dentro do nosso workflow.

  className="max-w-160"
/>

</Step>
