Neste capítulo, criamos nosso primeiro job do Expo Workflows.

## Objetivos de aprendizado \{#learning-outcomes}

- Criar e rodar um workflow personalizado que imprime uma mensagem no painel da Expo
- Configurar um gatilho automático para que cada push para `main` rode o workflow
- Encadear vários jobs para que a saída de um alimente o próximo
- Ler os logs do workflow e os grafos de jobs no painel da Expo

## Como os arquivos de workflow funcionam \{#how-workflow-files-work}

Os arquivos de workflow são arquivos YAML guardados na pasta **.eas/workflows/** do nosso projeto. Cada arquivo define os jobs a rodar e as etapas que cada job segue.

<JobTypes />

Um arquivo de workflow contém um ou mais jobs e um gatilho opcional. Quando roda, o Expo Workflows lê o arquivo, prepara o ambiente e executa os jobs nele.

## Tipos de job no Expo Workflows \{#types-of-jobs-in-expo-workflows}

O Expo Workflows tem dois tipos de job:

- **Job pré-empacotado:** usa o campo `type`. Ele diz ao Expo Workflows qual operação executar, como `build`, `submit` ou `update`. Depois, o Expo Workflows executa as etapas pré-configuradas dessa operação.
- **Job personalizado:** usa `steps` no lugar do campo `type`. Escrevemos nossos próprios comandos usando `run` em cada etapa. Um job personalizado nos dá controle sobre o que acontece quando um workflow roda e sobre quando executar um comando específico.

## Crie nosso primeiro workflow \{#create-our-first-workflow}

Vamos criar nosso primeiro workflow usando um job personalizado e rodá-lo no Expo Workflows.

<Step label="1">

### Crie a pasta de workflows \{#create-the-workflow-directory}

Crie a pasta **.eas/workflows/** na raiz do nosso projeto Expo. O Expo Workflows procura arquivos de workflow só nesse lugar.

<Terminal cmd={['$ mkdir -p .eas/workflows']} />

</Step>

<Step label="2">

### Adicione um arquivo hello.yml \{#add-a-helloyml-file}

Dentro de **.eas/workflows/**, crie um arquivo chamado **hello.yml**. Este arquivo define nosso primeiro workflow, com um único job personalizado. O job roda um comando de shell que imprime `"Hello, Workflows"`:

```yaml .eas/workflows/hello.yml
name: Hello

jobs:
  greet:
    steps:
      - run: echo "Hello, Workflows" # Any shell command works here
```

O workflow acima usa a seguinte sintaxe:

- `name` é o nome do workflow, como aparece no painel da Expo.
- `jobs` contém um ou mais jobs para rodar. Cada job tem um ID único (neste caso, `greet`).
- `steps` é uma sequência de tarefas que o job executa em ordem. Um job com `steps` e sem campo `type` é um job personalizado.
- `run` é o comando de shell a executar em uma etapa. Aqui, ele roda `echo` para imprimir uma mensagem. Qualquer comando de shell funciona.

</Step>

<Step label="3">

### Rode o workflow manualmente \{#manually-run-the-workflow}

Para rodar o workflow no painel da Expo, execute o comando a seguir em uma janela do terminal:

<Terminal cmd={['$ eas workflow:run .eas/workflows/hello.yml']} />

O comando `eas workflow:run` envia o arquivo de workflow para o Expo Workflows. Em seguida, ele roda qualquer job definido no arquivo, e o EAS CLI imprime uma URL para o painel da Expo, onde podemos acompanhar o job.

</Step>

<Step label="4">

### Veja os logs do job \{#view-the-job-logs}

Abra a URL da etapa anterior em um navegador. Na página do workflow, vemos o job `greet` e o status dele. Quando o job terminar, expanda a saída da etapa para ver a mensagem registrada: `Hello, Workflows`.

<ContentSpotlight
  alt="Painel do Expo Workflows mostrando os logs expandidos do job de uma execução do workflow Hello World."
  src="/static/images/tutorial/cicd/eas-workflows-job-logs-dashboard.png"
  className="max-w-160"
/>

O painel da Expo é onde vemos e fazemos debug de qualquer job de workflow. O **Workflow graph** mostra o que disparou nosso job e o ID único do job.

Troque para a aba **Workflow file**. Este é o arquivo de workflow que escrevemos na etapa 2, preservado com a execução.

> **info** **Dica:** veja todos os workflows do projeto e filtre-os por status ou tipo na [página de Workflows](https://expo.dev/accounts/[account]/projects/[project]/workflows).

</Step>

## Rode um workflow automaticamente \{#automatically-run-a-workflow}

Rodar `eas workflow:run` no terminal serve para uma execução pontual, mas a maioria das equipes quer workflows que disparem sozinhos com eventos do GitHub. Gatilhos automáticos significam que ninguém precisa lembrar de rodar um workflow. A configuração do workflow fica no repositório, junto com o código que ele gera.

> **info** **Nota:** um gatilho é uma regra que diz a um pipeline de CI/CD quando começar. Ele define o evento (como um push de código ou um pull request) que faz o pipeline rodar automaticamente, em vez de exigir execução manual.

Definimos um gatilho com a chave `on` no arquivo de workflow. O Expo Workflows observa o evento correspondente do GitHub e roda o workflow automaticamente.

<Step label="1">

### Adicione um gatilho automático \{#add-an-automatic-trigger}

Vamos adicionar um gatilho `on.push.branches` ao nosso arquivo de workflow existente.

- A chave `on` define qual evento do GitHub dispara o workflow
- O campo `push` define quando disparar
- O campo `branches` permite especificar que, sempre que o código for enviado para a branch `main`, o workflow deve rodar automaticamente

```yaml .eas/workflows/hello.yml
name: Hello

# @info #
on:
  push:
    branches: ['main'] # Fires on every push to main branch
# @end #

jobs:
  greet:
    steps:
      - run: echo "Hello, Workflows"
```

O campo `branches` pode incluir qualquer nome de branch que exista em um repositório do GitHub. Podemos especificar várias branches, como `['main', 'develop', 'staging']`, para disparar o workflow quando enviarmos código para qualquer uma delas.

</Step>

<Step label="2">

### Faça o commit da mudança e envie ao GitHub \{#commit-the-change-and-push-to-github}

Faça o commit do arquivo de workflow e envie-o para a branch `main`:

<Terminal
  cmd={[
    '$ git add .eas/workflows/hello.yml',
    '$ git commit -m "Add hello workflow"',
    '$ git push origin main',
  ]}
  cmdCopy="git add .eas/workflows/hello.yml && git commit -m 'Add hello workflow' && git push origin main"
/>

</Step>

<Step label="3">

### Verifique o gatilho automático \{#verify-the-automatic-trigger}

> **info** **Dica:** esta etapa depende de o projeto Expo local estar enviado ao GitHub e de o repositório estar conectado aos Expo Services. Para confirmar: rode `git remote -v` para verificar se o repositório local aponta para uma URL do GitHub, e abra as [configurações do GitHub no painel da Expo](https://expo.dev/accounts/[account]/projects/[projectName]/github) para checar se um repositório está conectado.

Vamos abrir a [página de Workflows](https://expo.dev/accounts/[account]/projects/[project]/workflows) do nosso projeto no painel da Expo para ver o novo job.

<ContentSpotlight
  alt="Painel do Expo Workflows mostrando uma execução de workflow disparada automaticamente por um push para a branch main do repositório do GitHub."
  src="/static/images/tutorial/cicd/eas-workflows-github-triggered-run.png"
  className="max-w-160"
/>

No painel da Expo, repare que a aba **Workflow graph** mostra a mensagem de commit e a referência da branch deste push. No status abaixo do cabeçalho do workflow, **Trigger** e **Triggered by** mostram as mesmas informações.

</Step>

## Outros tipos de gatilho \{#other-trigger-types}

Outros tipos de gatilho que usamos mais adiante neste tutorial:

- `on.pull_request`: roda quando um pull request é aberto ou atualizado em uma branch correspondente
- `on.push` com `tags`: roda quando um padrão de tag correspondente é enviado ao repositório do GitHub
- `on.pull_request_labeled`: roda quando um label específico é adicionado a um pull request

## Encadeie os jobs \{#chain-jobs-together}

Até agora, implementamos um único job no nosso arquivo de workflow. Um arquivo de workflow pode ter vários jobs, e a entrada de um job pode depender da saída do anterior. Vamos encadear vários jobs em um arquivo de workflow.

<Step label="1">

### Atualize o hello.yml \{#update-helloyml}

Vamos atualizar o arquivo **hello.yml** para adicionar um job personalizado e um job pré-empacotado. Esse job pré-empacotado se chama [`doc`](/eas/workflows/pre-packaged-jobs/#doc) e renderiza Markdown no painel da Expo:

```yaml .eas/workflows/hello.yml
name: Hello

jobs:
  greet:
    # @info #
    outputs:
      greeting: ${{ steps.set_greeting.outputs.greeting }} # Expose the step output at the job level
    # @end #
    steps:
      - id: set_greeting
        run: set-output greeting "Hello from Expo Workflows"
  show_info:
    # @info #
    needs: [greet] # Wait for greet to finish, then read its outputs
    type: doc # Pre-packaged job that renders Markdown on the dashboard
    # @end #
    params:
      md: |
        # Workflow Output
        **${{ needs.greet.outputs.greeting }}**
```

O arquivo de workflow acima faz o seguinte:

- Define um job `greet`, que é um job personalizado. Ele usa a função de shell [`set-output`](/eas/workflows/syntax/#set-output) para definir um valor chamado `greeting`. O campo `outputs` no nível do job expõe a saída da etapa para que outros jobs possam referenciá-la.
- Define um job `show_info`, que usa `needs: [greet]` para esperar o job `greet` terminar e acessar a saída dele. Depois, usa o tipo de job pré-empacotado `doc` para renderizar um documento Markdown no painel da Expo. O conteúdo Markdown inclui o valor de `greeting` definido no job anterior.

> **info** **Dica:** no Expo Workflows, os jobs rodam em paralelo por padrão. O campo `needs` é o que faz um job esperar: ele lista os IDs de jobs que precisam terminar com sucesso antes de o job que usa `needs` começar. Se um job da lista `needs` falhar, o job dependente é pulado.

</Step>

<Step label="2">

### Rode o workflow encadeado \{#run-the-chained-workflow}

Rode o comando a seguir em uma janela do terminal para ver os jobs encadeados em ação:

<Terminal cmd={['$ eas workflow:run .eas/workflows/hello.yml']} />

Abra o link do painel da Expo que o EAS CLI mostra. Em **Logs**, repare que o job `greet` roda primeiro. Quando ele termina, o job `show_info` roda e renderiza o conteúdo Markdown usando a saída do job anterior.

<ContentSpotlight
  alt="Painel do Expo Workflows mostrando dois jobs encadeados rodando em sequência, depois que o primeiro job termina."
  src="/static/images/tutorial/cicd/eas-workflows-chained-jobs.png"
  className="max-w-160"
/>

</Step>

## Limpeza \{#clean-up}
