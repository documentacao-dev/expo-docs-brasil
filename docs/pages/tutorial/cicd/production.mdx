Refazer o build do app a cada mudança de produção é desperdício quando a maioria das mudanças é só em TypeScript/JavaScript.

## O que você vai aprender

- Disparar deploys de produção a partir de uma branch `release/*`, em vez de a cada push na `main`
- Escolher entre um build nativo e uma [atualização OTA](/deploy/send-over-the-air-updates/) com base no fingerprint do projeto
- Automatizar o envio para as lojas de apps como uma etapa seguinte do workflow de produção

<Prerequisites>

<Requirement title="Expo Build configurado para produção">

A [EAS CLI](/eas/cli/) pede para gerar as credenciais na primeira vez que disparamos um build para um perfil. Dispare o build de produção manualmente para Android e iOS para que as credenciais existam antes de o workflow rodar:

<Terminal cmd={['$ eas build --profile production --platform all']} />

</Requirement>

</Prerequisites>

## Usando uma branch de release

Antes, com os development builds, vimos que usar o trigger `on.push.branches` faz o workflow rodar a cada push na branch `main` especificada. Para deploys de produção, disparar um workflow a cada push na `main` significa que cada mudança mesclada vira um release novo. Os times costumam querer um processo de release deliberado, então usam uma branch ou tag de release.

Em uma estratégia com branch de release, normalmente especificamos a branch com um padrão como `release/*`, em que `*` é o nome da funcionalidade ou da versão. É isso que separa Integração Contínua (CI) de Entrega Contínua (CD). O CI roda a cada push na branch `main`, enquanto o CD roda em uma branch de release quando o time está pronto para publicar em produção.

A tabela abaixo mostra como o trigger de cada workflow define a sua finalidade:

| Arquivo do workflow              | Trigger                           | Perfil de build | Finalidade                                                                                                                                                   |
| -------------------------------- | --------------------------------- | --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **.eas/workflows/build.yml**      | `on.push.branches: ['main']`      | `development`   | Workflow de CI que roda a cada push na branch `main`. Pode rodar testes unitários e gerar development builds.                                                |
| **.eas/workflows/preview.yml**    | `on.push.branches: ['main']`      | `preview`       | Workflow de preview que roda a cada push na branch `main`. Pode gerar preview builds para testes internos e para compartilhar com stakeholders.              |
| **.eas/workflows/production.yml** | `on.push.branches: ['release/*']` | `production`    | Workflow de CD que roda a cada push em uma branch de release.                                                                                                 |

Os arquivos acima coexistem no repositório do GitHub do projeto sem nenhum conflito. Cada um usa um perfil de build e um trigger diferentes.

## O job `build` para builds de produção

Vamos começar criando um workflow de produção. Ele usa o tipo de job `build` [pré-empacotado](/tutorial/cicd/first-workflow/#types-of-jobs-in-expo-workflows) do Expo Workflows e roda para Android e iOS.

<Step label="1">

### Adicione um production.yml

Dentro de **.eas/workflows/**, crie um novo arquivo chamado **production.yml** que usa o perfil de build `production` do **eas.json**:

```yaml .eas/workflows/production.yml
name: Deploy to production

on:
  push:
    branches: ['release/*']

jobs:
  build_android:
    name: Build Android
    type: build
    params:
      platform: android
      profile: production
  build_ios:
    name: Build iOS
    type: build
    params:
      platform: ios
      profile: production
```

Isso cria um artefato **.aab** para Android e um artefato **.ipa** para iOS a cada push em qualquer branch que corresponda ao padrão `release/*`.

</Step>

<Step label="2">

### Adicione fingerprints ao workflow

Vamos adicionar um job [`fingerprint`](/eas/workflows/pre-packaged-jobs/#fingerprint) ao workflow para verificar se há mudanças no código nativo e atualizar os jobs `build_android` e `build_ios` existentes com base nisso. Também estamos adicionando jobs [`get-build`](/eas/workflows/pre-packaged-jobs/#get-build) para procurar builds existentes para Android e iOS.

Atualize o arquivo **production.yml** com o código a seguir:

```yaml .eas/workflows/production.yml
name: Deploy to production

on:
  push:
    branches: ['release/*']

jobs:
  # @info #
  fingerprint:
    name: Fingerprint
    type: fingerprint
    environment: production
  # @end #
  # @info #
  get_android_build:
    name: Check for existing Android build
    needs: [fingerprint]
    type: get-build
    params:
      fingerprint_hash: ${{ needs.fingerprint.outputs.android_fingerprint_hash }}
      profile: production
  get_ios_build:
    name: Check for existing iOS build
    needs: [fingerprint]
    type: get-build
    params:
      fingerprint_hash: ${{ needs.fingerprint.outputs.ios_fingerprint_hash }}
      profile: production
  # @end #
  build_android:
    name: Build Android
    needs: [get_android_build]
    # @info #
    if: ${{ !needs.get_android_build.outputs.build_id }}
    # @end #
    type: build
    params:
      platform: android
      profile: production
  build_ios:
    name: Build iOS
    needs: [get_ios_build]
    # @info #
    if: ${{ !needs.get_ios_build.outputs.build_id }}
    # @end #
    type: build
    params:
      platform: ios
      profile: production
```

No workflow acima, o job `fingerprint` roda primeiro e gera um hash com base nas mudanças do código. Depois, os jobs `get-build` verificam se já existem builds para Android e iOS com o mesmo hash de fingerprint. Se não existirem builds, os jobs `build` rodam para criar builds novos de produção.

O campo [`environment`](/eas/workflows/syntax/#jobsjob_idenvironment) no job `fingerprint` diz ao Expo Workflows quais variáveis de ambiente carregar ao calcular o fingerprint. Nosso ambiente de produção pode ter valores diferentes para variáveis como `API_URL` ou feature flags. Esses valores podem afetar a camada nativa quando o Expo Build os incorpora ao build. Definir `environment: production` garante que o fingerprint reflita o que vai para as lojas.

O campo [`if`](/eas/workflows/syntax/#jobsjob_idif) usado nos jobs `build_android` e `build_ios` é uma expressão booleana. Quando ela resulta em `false`, os jobs de build são pulados. O operador `!` faz com que o job de build só rode quando o `get-build` não encontrou um build correspondente.

</Step>

<Step label="3">

### Adicione jobs para atualizações

Por enquanto, nosso workflow só cria builds de produção quando há mudanças no código nativo. Se houver apenas mudanças em arquivos TypeScript/JavaScript, queremos disparar uma atualização OTA em vez de um build nativo.

Vamos adicionar dois jobs, `update_android` e `update_ios`, que rodam quando não há mudanças no código nativo e usam o tipo de job `update` para disparar uma atualização OTA:

```yaml .eas/workflows/production.yml
name: Deploy to production

on:
  push:
    branches: ['release/*']

jobs:
  fingerprint:
    # ...
  get_android_build:
    # ...
  get_ios_build:
    # ...
  build_android:
    # ...
  build_ios:
    # ...
  update_android:
    name: Publish Android update
    needs: [get_android_build]
    if: ${{ needs.get_android_build.outputs.build_id }}
    type: update
    params:
      branch: production
      platform: android
  update_ios:
    name: Publish iOS update
    needs: [get_ios_build]
    if: ${{ needs.get_ios_build.outputs.build_id }}
    type: update
    params:
      branch: production
      platform: ios
```

Nosso workflow só gera binários de app prontos para produção ou publica atualizações OTA. Automatizar o envio para as lojas é um próximo passo comum, discutido abaixo na seção [Automatize o envio para as lojas de apps](#automate-app-store-submissions).

</Step>

<Step label="4">

### Crie uma branch de release e faça push das mudanças

> **info** **Observação:** confirme que o arquivo do workflow já faz parte do repositório do GitHub e está disponível na branch `main` neste momento.

Para testar nosso workflow, vamos criar uma branch de release e enviá-la ao repositório do GitHub pelo terminal:

<Terminal
  cmd={['$ git checkout -b release/1.0.0', '', '$ git push origin release/1.0.0']}
  cmdCopy="git checkout -b release/1.0.0 && git push origin release/1.0.0"
/>

Abra o dashboard da Expo e encontre a execução do workflow. Como ainda não existe build para este fingerprint, os jobs `build` devem rodar, e os jobs `update` devem aparecer em cinza.

<ContentSpotlight
  alt="Dashboard do Expo Workflows mostrando uma execução de produção em branch de release com fingerprint, get-build e os jobs de build de Android e iOS."
  src="/static/images/tutorial/cicd/eas-workflows-production-build-jobs.png"
  className="max-w-160"
/>

Os builds de Android e iOS rodam em paralelo. Quando cada job termina, recebemos um novo artefato para Android e iOS.

Agora, vamos fazer uma mudança só em TypeScript/JavaScript no projeto de exemplo, na mesma branch de release, e fazer push de novo com os comandos abaixo:

<Terminal
  cmd={['$ git add .', '$ git commit -m "Update welcome text"', '$ git push origin release/1.0.0']}
  cmdCopy="git add . && git commit -m 'Update welcome text' && git push origin release/1.0.0"
/>

Depois que o workflow rodar, observe no dashboard da Expo que o fingerprint bate com o build do último push. Os jobs `build` são pulados por completo, e os jobs `update` publicam uma atualização OTA.

  alt="Execução de produção do Expo Workflows reaproveitando builds nativos existentes pela correspondência do fingerprint e publicando atualizações over-the-air para Android e iOS."

  className="max-w-160"
/>

</Step>

## Automatize o envio para as lojas de apps

O workflow que construímos neste capítulo só gera binários de app prontos para produção ou publica atualizações OTA para um app de produção já existente. [Automatizar o envio para as lojas](/build/automate-submissions/) é um próximo passo comum em um workflow de release de produção.

O Expo Workflows oferece um job `submit` pré-empacotado para automatizar o envio para as lojas de apps. Ele exige que gerenciemos as credenciais das lojas com a EAS CLI. Também exige que cumpramos os requisitos das lojas, como enviar manualmente a primeira versão Android (**.aab**) para a Google Play Store. O iOS tem a sua própria inscrição no Apple Developer Program e as credenciais de assinatura para configurar.

Quando os requisitos das lojas estiverem resolvidos, podemos adicionar ao nosso workflow dois novos jobs, `submit_android` e `submit_ios`, que rodam depois dos jobs `build`:

```yaml .eas/workflows/production.yml
# rest of the workflow file

submit_android:
  name: Submit Android
  needs: [build_android]
  type: submit
  params:
    build_id: ${{ needs.build_android.outputs.build_id }}
submit_ios:
  name: Submit iOS
  needs: [build_ios]
  type: submit
  params:
    build_id: ${{ needs.build_ios.outputs.build_id }}
```

Os jobs `submit_android` e `submit_ios` acima exigem o parâmetro `build_id` para saber qual build enviar para as lojas. Eles só rodam quando os jobs `build_android` e `build_ios` rodam, ou seja, quando um build de produção novo é criado. Se houver apenas mudanças em arquivos TypeScript/JavaScript, os jobs `submit` também são pulados, já que nenhum build novo é criado.
