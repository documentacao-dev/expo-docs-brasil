Os workflows dos capítulos anteriores cobrem Android e iOS. Vamos estendê-los para também publicar o build web no [Expo Hosting](/eas/hosting/introduction/), junto com o mesmo release.

## O que você vai aprender

- Configurar o projeto Expo para exportar um build web estático
- Adicionar um job de deploy web ao **preview.yml** para gerar um build web que não é de produção
- Adicionar um job de deploy web ao **production.yml** para gerar um build web de produção

## Expo Hosting e o job deploy

O **Expo Hosting** é um serviço para hospedar e publicar builds web de um app Expo. Cada deploy ganha uma URL própria e única, e um projeto tem uma única URL de produção, que serve o que publicamos por último em produção.

O job pré-empacotado [`deploy`](/eas/workflows/pre-packaged-jobs/#deploy) do Expo Workflows roda a exportação web, envia a saída da etapa de exportação para o Expo Hosting e devolve a URL do deploy como saída do job. O job `deploy` tem dois parâmetros:

| Parâmetro | Tipo    | Descrição                                                                                                    |
| --------- | ------- | ------------------------------------------------------------------------------------------------------------ |
| `prod`    | boolean | Opcional. Se `true`, publica na URL de produção do projeto. Se omitido, publica como preview.                |
| `alias`   | string  | Opcional. Dá um nome a uma URL de alias estável, como `awesome-project--staging.expo.app`.                   |

## Configure o web.output para exportação estática

Antes de adicionar jobs de deploy web aos nossos workflows, precisamos configurar o projeto Expo para exportar um [build web estático](/router/web/static-rendering/). No **app.json**, defina o campo [`web.output`](/versions/latest/config/app/#web) como `static`:

```json app.json
{
  "expo": {
    /* @hide ... */ /* @end */
    "web": {
      "output": "static"
    }
  }
}
```

`static` faz a Expo CLI produzir um diretório com arquivos HTML, JavaScript e assets estáticos que o Expo Hosting consegue servir. A Expo também oferece suporte às saídas `single` e `server`, mas `static` gera arquivos simples que qualquer host consegue servir, e isso é tudo o que precisamos aqui.

Depois de atualizar o **app.json** com a configuração acima, faça commit da mudança e envie para a branch `main` do repositório.

## Adicione um deploy de preview web

Definir `prod: true` é a diferença entre um deploy de preview e um deploy de produção. Os previews ganham URLs únicas por deploy. Criamos um workflow de preview no [Capítulo 3, passo 1](/tutorial/cicd/preview-builds/#add-a-previewyml). Vamos adicionar um job `deploy_web` a esse workflow, para que, sempre que criarmos um novo preview build, ganhemos também um novo deploy web.

<Step label="1">

### Adicione um job deploy_web

Abra o **.eas/workflows/preview.yml** e adicione um job `deploy_web`. Esse novo job roda em paralelo com os jobs de build existentes, porque não tem nenhuma dependência em `needs`.

```yaml .eas/workflows/preview.yml
name: Preview builds

jobs:
  # ... existing fingerprint, get-build, build_android, build_ios, notify jobs

  deploy_web:
    name: Deploy web (preview)
    type: deploy
```

Sem o parâmetro `prod`, o deploy é feito como uma versão que não é de produção. Cada push ganha uma URL única, como `https://awesome-project--abc123.expo.app`.

</Step>

<Step label="2">

### Envie a mudança do workflow para o repositório

Faça commit da mudança no **preview.yml** e envie para a branch `main` do repositório no GitHub. O Expo Workflows lê os arquivos de workflow da branch padrão, então é isso que faz a mudança valer.

<Terminal
  cmd={[
    '$ git add .eas/workflows/preview.yml',
    '',
    '$ git commit -m "Add web preview deploy job to preview workflow"',
    '',
    '$ git push origin main',
  ]}
  cmdCopy="git add .eas/workflows/preview.yml && git commit -m 'Add web preview deploy job to preview workflow' && git push origin main"
/>

</Step>

<Step label="3">

### Teste o workflow

Agora, rode manualmente o workflow de preview com o comando a seguir:

<Terminal cmd={['$ eas workflow:run .eas/workflows/preview.yml']} />

No dashboard da Expo, a execução do workflow de preview mostra o job `deploy_web` ao lado dos jobs de build.

  className="max-w-160"
/>

Em **Deploy web (preview)**, clique no link **View Deployment** para abrir o build web publicado no navegador.

<ContentSpotlight

## Adicione um deploy web de produção

O workflow de produção do [Capítulo 6, passo 1](/tutorial/cicd/tag-based-releases/#change-the-trigger) roda quando enviamos uma nova tag do Git, e ele gera ou atualiza o app nativo. Vamos adicionar um job `deploy_web` a esse workflow, para que lançar uma nova versão do app também atualize a versão web na URL de produção.

<Step label="1">

### Adicione um job deploy_web

Abra o **.eas/workflows/production.yml** e adicione um job `deploy_web`. Esse novo job roda em paralelo com os jobs de build existentes, porque não tem nenhuma dependência em `needs`.

```yaml .eas/workflows/production.yml
name: Deploy to production

on:
  push:
    tags: ['v*.*.*']

jobs:
  # ... existing fingerprint, get-build, build, update jobs ...

  deploy_web:
    name: Deploy web (production)
    type: deploy
    params:
      prod: true
```

No workflow acima, o padrão `['v*.*.*']` corresponde a versões semânticas estritas, com três partes. O `params.prod: true` publica o app web na URL de produção, como `https://awesome-project.expo.app`.

</Step>

<Step label="2">

### Crie uma tag para testar o workflow

Faça commit da mudança do workflow na branch `main` do repositório:

<Terminal
  cmd={[
    '$ git add .eas/workflows/production.yml',
    '',
    '$ git commit -m "Add web production deploy to production workflow"',
    '',
    '$ git push origin main',
  ]}
  cmdCopy="git add .eas/workflows/production.yml && git commit -m 'Add web production deploy to production workflow' && git push origin main"
/>

Para rodar o workflow, crie uma nova tag e envie-a para o repositório:

<Terminal
  cmd={['$ git tag v0.2.0', '', '$ git push origin v0.2.0']}
  cmdCopy="git tag v0.2.0 && git push origin v0.2.0"
/>

Agora, o workflow de produção roda no lançamento da tag `v0.2.0`. O job `deploy_web` publica o build web na URL de produção.

</Step>
