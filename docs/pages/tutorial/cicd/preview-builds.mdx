Compartilhar mudanças mobile em andamento com colegas de time e com quem revisa pull requests (PR) costuma exigir que eles façam checkout de uma branch e rodem um servidor de desenvolvimento localmente.

## O que você vai aprender

- Automatizar preview builds com fingerprint para distribuição interna
- Enviar notificações no Slack quando um build terminar
- Publicar uma [atualização OTA](/deploy/send-over-the-air-updates/) em cada pull request e comentar no PR com um link para testá-la

<Prerequisites>

<Requirement title="expo-updates instalado">

Instale a biblioteca [`expo-updates`](/versions/latest/sdk/updates/):

<Terminal
  cmd={{
    npm: ['$ npx expo install expo-updates'],
    yarn: ['$ yarn dlx expo install expo-updates'],
    pnpm: ['$ pnpm dlx expo install expo-updates'],
    bun: ['$ bunx expo install expo-updates'],
  }}
/>

</Requirement>

<Requirement title="Expo Update configurado">

Para configurar o Expo Update, rode:

<Terminal cmd={['$ eas update:configure']} />

O comando acima adiciona a URL de update e a runtime version ao **app.json**, e adiciona um campo [`channel`](/eas-update/deployment/) a cada perfil de build no **eas.json**.

</Requirement>

<Requirement title="Preview build criado">

Para receber as atualizações de preview de PR, quem revisa precisa de um preview build com `expo-updates` e o channel do Expo Update instalados no dispositivo. Para criar um:

<Terminal cmd={['$ eas build --profile preview --platform all']} />

Como o `expo-updates` é uma biblioteca nativa, esse build incorpora tanto o código nativo dela quanto o channel do **eas.json**. Rodar o comando acima também permite que a EAS CLI gere as [credenciais](/app-signing/app-credentials/) na primeira vez que dispararmos um preview build.

</Requirement>

</Prerequisites>

## O job `build` para preview builds

Os times usam preview builds para testes com stakeholders. Os membros instalam o build pela distribuição interna no dispositivo, emulador ou simulador. Eles não precisam rodar um servidor de desenvolvimento nem fazer checkout da branch para testar as mudanças.

<PreviewPipeline />

Como nos [development builds](/tutorial/cicd/development-builds/#skip-unnecessary-builds-with-fingerprints), adicionamos fingerprints para evitar rebuilds desnecessários quando o código nativo não muda.

<Step label="1">

### Adicione um preview.yml

Dentro de **.eas/workflows/**, vamos adicionar um novo arquivo chamado **preview.yml**. Este arquivo de workflow usa o perfil `preview`.

```yaml .eas/workflows/preview.yml
name: Preview builds

jobs:
  fingerprint:
    name: Fingerprint
    type: fingerprint
    # @info #
    environment: preview
    # @end #
  get_android_build:
    name: Check for existing Android build
    needs: [fingerprint]
    type: get-build
    params:
      fingerprint_hash: ${{ needs.fingerprint.outputs.android_fingerprint_hash }}
      # @info #
      profile: preview
      # @end #
  get_ios_build:
    name: Check for existing iOS build
    needs: [fingerprint]
    type: get-build
    params:
      fingerprint_hash: ${{ needs.fingerprint.outputs.ios_fingerprint_hash }}
      # @info #
      profile: preview
      # @end #
  build_android:
    name: Build Android
    needs: [get_android_build]
    if: ${{ !needs.get_android_build.outputs.build_id }}
    type: build
    params:
      platform: android
      # @info #
      profile: preview
      # @end #
  build_ios:
    name: Build iOS
    needs: [get_ios_build]
    if: ${{ !needs.get_ios_build.outputs.build_id }}
    type: build
    params:
      platform: ios
      # @info #
      profile: preview
      # @end #
```

</Step>

<Step label="2">

### Rode o workflow

Rode o workflow manualmente com o comando a seguir:

<Terminal cmd={['$ eas workflow:run .eas/workflows/preview.yml']} />

No dashboard da Expo, veja que o workflow segue o mesmo padrão de fingerprint que implementamos para os [development builds](/tutorial/cicd/development-builds/#skip-unnecessary-builds-with-fingerprints). Como estamos criando o preview build pela primeira vez, ele roda os jobs de build de Android e iOS. Se fizermos push de outro commit para a branch `main` sem mudar o código nativo, o workflow pula os jobs de build, porque já existem builds compatíveis.

<ContentSpotlight
  alt="Execução de preview do Expo Workflows em que os jobs de fingerprint e get-build pulam os jobs de build porque já existem builds compatíveis de Android e iOS."
  src="/static/images/tutorial/cicd/eas-workflows-preview-fingerprint-skip.png"
  className="max-w-160"
/>

</Step>

## Notificações no Slack

> **info** Esta seção é opcional. Não usa Slack? Pule para a próxima seção, sobre previews de PR.

Muitos times usam o Slack para notificações de build, para que todos vejam o status sem precisar abrir o dashboard da Expo. Quando um build termina (ou é pulado), o job pré-empacotado [`slack`](/eas/workflows/pre-packaged-jobs/#slack) publica o status em um canal.

<Step label="1">

### Crie uma URL de webhook do Slack

Para enviar mensagens do Expo Workflows para o nosso canal do Slack, precisamos de uma URL de webhook das configurações do Slack:

1. Acesse [api.slack.com/apps](https://api.slack.com/apps) e crie um novo app do Slack (ou use um existente).
2. Em **Features**, selecione **Incoming Webhooks** e ative a opção.
3. Clique em **Add New Webhook** e selecione o canal para publicar as notificações.
4. Copie a URL do webhook. Ela tem este formato: `https://hooks.slack.com/services/TD000/B000/XXXXXXXXXX`
5. Adicione a URL do webhook como uma variável de ambiente dos Serviços da Expo chamada `SLACK_WEBHOOK_URL`. Abra a página [Environment variables](https://expo.dev/accounts/[account]/projects/[project]/environment-variables) do nosso projeto no dashboard da Expo, crie a variável para o ambiente `preview` e defina a sua [visibilidade](/eas/environment-variables/#visibility-settings-for-environment-variables) como **secret**, já que só os servidores da Expo precisam lê-la. Como alternativa, crie-a com a [EAS CLI](/eas/environment-variables/manage/):

<Terminal
  cmd={[
    '$ eas env:set --name SLACK_WEBHOOK_URL --value https://hooks.slack.com/services/TD000/B000/XXXXXXXXXX --environment preview --visibility secret',
  ]}
/>

</Step>

<Step label="2">

### Adicione um job de notificação no Slack

Vamos atualizar o **preview.yml** para adicionar um job `notify` depois dos jobs de build. O job `notify` usa os parâmetros `webhook_url` e `message`, ou um parâmetro `payload` para formatação rica com o [Slack Block Kit](https://docs.slack.dev/block-kit). O job lê a URL do webhook da [variável de ambiente `SLACK_WEBHOOK_URL` que criamos antes](#create-a-slack-webhook-url), pelo campo `environment`. Os jobs usam o ambiente `production` por padrão, então definir `environment: preview` aqui é o que disponibiliza a variável.

```yaml .eas/workflows/preview.yml
name: Preview builds

jobs:
  fingerprint: # ...
  get_android_build: # ...
  get_ios_build: # ...
  build_android: # ...
  build_ios: # ...
  # @info #
  notify:
    name: Notify on Slack
    after: [build_android, build_ios]
    type: slack
    environment: preview
    params:
      webhook_url: ${{ env.SLACK_WEBHOOK_URL }}
      message: 'Preview builds are ready - Android: ${{ after.build_android.status }}, iOS: ${{ after.build_ios.status }}'
  # @end #
```

O campo `after` garante que a notificação saia quando os builds terminarem, independentemente do resultado. A `message` usa `${{ after.build_android.status }}` e `${{ after.build_ios.status }}` para incluir o resultado de cada plataforma (sucesso, falha ou pulado). Assim, o time vê o que aconteceu sem sair do Slack.

</Step>

<Step label="3">

### Rode o workflow

Rode o workflow manualmente com o comando a seguir:

<Terminal cmd={['$ eas workflow:run .eas/workflows/preview.yml']} />

No dashboard da Expo, podemos verificar se o job `Notify on Slack` roda com sucesso.

<ContentSpotlight
  alt="Execução de preview do Expo Workflows mostrando o job Notify on Slack concluído com sucesso depois dos jobs de build de Android e iOS."
  src="/static/images/tutorial/cicd/eas-workflows-preview-slack-notify-job.png"
  className="max-w-160"
/>

Também podemos conferir no canal do Slack integrado ao app.

## Previews de PR usando Expo Update

Quem revisa um PR consegue ler o diff, mas não consegue ver as mudanças visualmente nem testá-las em um dispositivo.

Times web resolvem isso com deploy previews. Quando alguém abre um pull request, um workflow de CI/CD gera um link de preview. Quem revisa abre o link e testa as mudanças sem fazer checkout da branch.

Para mobile, podemos montar o equivalente usando o [Expo Update](/eas-update/introduction/). Ele entrega um bundle de JavaScript para dispositivos que já têm um build compatível instalado, pulando a etapa de compilação nativa. Para previews de PR, uma atualização é a escolha certa, porque quem revisa consegue abrir e testar rápido e depois deixar feedback no PR.

O Expo Workflows oferece para isso o job pré-empacotado [`github-comment`](/eas/workflows/pre-packaged-jobs/#github-comment). Ele publica um comentário no pull request depois que a atualização é publicada, dando a quem revisa um link ou QR code para abrir a atualização no dispositivo.

<Step label="1">

### Crie um pr-preview.yml

Dentro de **.eas/workflows/**, vamos adicionar um novo arquivo chamado **pr-preview.yml**. Este workflow roda quando um pull request é criado, usando o trigger `on.pull_request`. Ele só publica uma atualização com o job do tipo `update` e depois publica um comentário no PR com o link da atualização.

```yaml .eas/workflows/pr-preview.yml
name: PR Preview

on:
  pull_request:
    branches: ['*']

jobs:
  publish_preview:
    name: Publish PR preview update
    type: update
    environment: preview
    params:
      channel: preview
  comment:
    needs: [publish_preview]
    type: github-comment
```

> **important** Antes de testar o workflow acima, faça commit do **pr-preview.yml** e envie-o para a branch `main` do nosso repositório no GitHub. **O Expo Workflows lê os arquivos de workflow da branch padrão.**

</Step>

<Step label="2">

### Teste com um pull request

Vamos testar o workflow criando um pull request no nosso repositório do GitHub. Um pull request exige uma branch separada da `main`. Rode o comando a seguir para criar uma nova branch e trocar para ela:

<Terminal cmd={['$ git checkout -b test-preview']} />

Agora, vamos fazer uma mudança visível no projeto Expo (por exemplo, trocar um texto ou a cor de fundo). Depois, faça commit e push da branch:

<Terminal
  cmd={['$ git add .', '$ git commit -m "Test PR preview"', '$ git push origin test-preview']}
  cmdCopy="git add . && git commit -m 'Test PR preview' && git push origin test-preview"
/>

Abra um pull request de `test-preview` para `main` no GitHub. O workflow roda automaticamente depois que criamos o pull request. No dashboard da Expo, podemos verificar se o job `publish_preview` roda primeiro e se o job `comment` roda depois que ele termina com sucesso.

<ContentSpotlight
  alt="Execução de preview de pull request do Expo Workflows mostrando o job publish_preview seguido pelo job comment, que publica o link da atualização no GitHub."
  src="/static/images/tutorial/cicd/eas-workflows-preview-pr-publish-comment.png"
  className="max-w-160"
/>

No pull request do GitHub, deve aparecer um comentário com um link ou QR code para testar a atualização no dispositivo.

<ContentSpotlight
  alt="Comentário no pull request do GitHub publicado pelo Expo Workflows, com link para um preview do Expo Update das mudanças propostas."
  src="/static/images/tutorial/cicd/eas-workflows-preview-github-pr-comment.png"
  className="max-w-160"
/>

Usando o link ou o QR code do comentário, já podemos abrir a atualização no dispositivo ou no emulador/simulador e testar as mudanças.

</Step>
