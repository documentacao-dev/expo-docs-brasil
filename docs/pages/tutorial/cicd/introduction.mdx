Construir, testar e entregar um app Expo ou React Native raramente é um processo de um passo só. Cada mudança de código passa por um fluxo parecido: gerar builds para Android e iOS, rodar testes unitários e de ponta a ponta (E2E) e entregar o resultado para colegas de equipe, QA ou para as lojas de apps. Fazer isso a cada commit fica cansativo rápido, e é exatamente o tipo de trabalho de que um pipeline de CI/CD deveria cuidar por nós.

Ao final deste tutorial, cada push para o nosso projeto Expo vai gerar builds, rodar testes ou publicar automaticamente. O serviço que torna isso possível é o [Expo Workflows](/eas/workflows/introduction/), um serviço de Integração Contínua (CI) e Entrega Contínua (CD) dos Expo Services para apps Expo e React Native.

Definimos um workflow em um arquivo [YAML](https://en.wikipedia.org/wiki/YAML) que fica na pasta **.eas/workflows/** na raiz do nosso projeto Expo. Veja um exemplo completo que gera uma development build para Android a cada push na branch `main` de um repositório do GitHub:

```yaml .eas/workflows/build.yml
name: Build Android

on:
  push:
    branches: ['main']

jobs:
  build:
    type: build
    params:
      platform: android
      profile: development
```

Essas poucas linhas são o workflow inteiro, e o Expo Workflows cuida do resto. Usamos esse padrão ao longo de todo o tutorial.

## Por que usar o Expo Workflows? \{#why-use-expo-workflows}

O Expo Workflows roda builds para Android, iOS e web, publica [atualizações OTA](/deploy/send-over-the-air-updates/), envia apps para as lojas e roda testes E2E com o Maestro, tudo definido em arquivos YAML como o exemplo acima. Como os jobs rodam em um ambiente gerenciado na nuvem, não há servidor de build para configurar ou manter.

Podemos disparar workflows a partir de eventos do GitHub (push, pull request, tags ou labels), em um agendamento (cron) ou manualmente com o [EAS CLI](/eas/cli/).

## Tópicos abordados \{#topics-covered}

O tutorial tem três partes:

- **Desenvolvimento.** Crie jobs personalizados, automatize [development builds](/develop/development-builds/introduction/) com [fingerprinting](/tutorial/cicd/development-builds/) e publique [atualizações de preview de pull request (PR)](/tutorial/cicd/preview-builds/) para as partes interessadas.
- **Testes e release.** Rode testes E2E com o Maestro em um workflow e depois crie um workflow de produção que usa fingerprinting para escolher entre uma build nativa e uma atualização OTA.
- **Extensões.** Troque os gatilhos de produção de branches para tags de versão e faça o deploy de builds web com o [Expo Hosting](/eas/hosting/introduction/).

## Conceitos que vale conhecer primeiro \{#concepts-worth-knowing-first}

> **info** **Dica:** já conhece o Expo Build e o Expo Update? Pule para a próxima seção.

Antes de criar nosso primeiro workflow, veja alguns conceitos que vale conhecer:

<Collapsible summary="Para onde um app Expo é entregue?">

Um app Expo pode ser entregue para três destinos. Qual deles, e qual serviço faz a entrega, depende do que mudou no código:

| Destino                 | Serviço                  | Quando usar                                                          |
| ----------------------- | ------------------------ | -------------------------------------------------------------------- |
| Lojas de apps           | Expo Build e Expo Submit | Novos releases, mudanças em código nativo                            |
| Dispositivos instalados | Expo Update              | Correções só em TypeScript/JavaScript, entregues via OTA em segundos |
| Web                     | Expo Hosting             | App web junto com os releases nativos                                |

</Collapsible>

<Collapsible summary="Perfis de build">

O [Expo Build](/build/introduction/) é um serviço para gerar binários de apps para os nossos projetos Expo. Ele oferece três perfis de build por padrão: `development`, `preview` e `production`. Cada perfil corresponde a uma etapa diferente do desenvolvimento. Usamos os três neste tutorial.

</Collapsible>

<Collapsible summary="Builds x updates">

Assim como o Expo Build, o [Expo Update](/eas-update/introduction/) é um serviço que entrega atualizações OTA para projetos Expo, usando a biblioteca [`expo-updates`](/versions/latest/sdk/updates/).

<BuildsVsUpdates />

- O Expo Build compila o código nativo em um binário completo do app. As builds levam mais tempo para rodar. Precisamos de uma nova build quando o código nativo do projeto muda, por exemplo ao adicionar uma biblioteca nativa, mudar permissões ou atualizar o Expo SDK.
- O Expo Update entrega mudanças em TypeScript/JavaScript via OTA para dispositivos que já têm uma build nativa compatível instalada. Se uma mudança exige código nativo, criamos e instalamos essa build antes de publicar uma atualização. Assim, cada atualização continua compatível com a build para a qual foi feita. Publicar a atualização em si leva segundos. Por exemplo, podemos publicar uma atualização para corrigir um bug de interface ou mudar o texto de um botão.

Dependendo da mudança, usamos um serviço ou outro. O Expo Workflows conecta os dois, para que o pipeline decida quando gerar uma build e quando publicar uma atualização.

</Collapsible>

## Pré-requisitos \{#prerequisites}

> **info** **Dica:** já tem um projeto Expo configurado com Expo Build e Expo Update? Pule para o próximo capítulo.

Este tutorial é prático. Para avançar, precisamos de um projeto Expo que use a [Geração Nativa Contínua](/workflow/continuous-native-generation/). Configure-o na nossa máquina e nos Expo Services com os requisitos a seguir:

<Prerequisites>

<Requirement title="Uma conta na Expo">

Precisamos [criar uma conta](https://expo.dev/signup) na Expo.

</Requirement>

<Requirement title="Instalar o EAS CLI e fazer login">

Para instalar o EAS CLI, rode o comando a seguir:

<Terminal
  cmd={{
    npm: ['$ npm install --global eas-cli'],
    yarn: ['$ yarn global add eas-cli'],
    pnpm: ['$ pnpm add -g eas-cli'],
    bun: ['$ bun add -g eas-cli'],
  }}
/>

Depois, rode o comando de login a seguir para autenticar o EAS CLI com a conta da Expo:

<Terminal cmd={['$ eas login']} />

</Requirement>

<Requirement title="Criar um projeto Expo">

Para criar um novo projeto Expo, rode o comando a seguir:

<Terminal
  cmd={{
    npm: ['$ npx create-expo-app@latest'],
    yarn: ['$ yarn create expo-app'],
    pnpm: ['$ pnpm create expo-app'],
    bun: ['$ bun create expo'],
  }}
/>

Criar um projeto com o `create-expo-app` gera um projeto sem os diretórios **android** e **ios** versionados. Esse padrão se chama Geração Nativa Contínua (CNG), e o Expo Build cria esses diretórios nativos automaticamente para nós.

</Requirement>

<Requirement title="Inicializar os Expo Services no projeto">

Para inicializar os Expo Services no nosso projeto, rode o comando a seguir:

<Terminal cmd={['$ eas build:configure']} />

Isso gera um arquivo **eas.json** na raiz do nosso projeto Expo e cria um projeto nos Expo Services vinculado ao nosso projeto local.

</Requirement>

<Requirement title="Repositório do GitHub conectado ao painel da Expo">

Precisamos de um repositório do GitHub para o projeto. Podemos criar um repositório novo ou usar um existente. Depois, conecte o repositório aos Expo Services:

1. Acesse as [configurações do GitHub](https://expo.dev/accounts/[account]/projects/[projectName]/github) do projeto no painel da Expo.
2. Siga a interface do painel para instalar o app do GitHub da Expo.
3. Selecione o repositório do GitHub que corresponde ao projeto Expo e conecte-o.

</Requirement>

<Requirement title="Credenciais de envio para as lojas, para o Expo Submit (opcional)">

Só é necessário se adicionarmos o envio automático para as lojas de apps como uma adaptação depois do Capítulo 5. Veja os guias da [Google Play Store](/submit/android/) e da [Apple App Store](/submit/ios/) para instruções sobre como configurar as credenciais do Expo Submit.

</Requirement>

</Prerequisites>

## Vindo do GitHub Actions? \{#coming-from-github-actions}

Os arquivos de workflow do Expo Workflows ficam na pasta **.eas/workflows/** na raiz de um projeto Expo, de forma parecida com os workflows do GitHub Actions em **.github/workflows/**. A sintaxe dos gatilhos (`on.push`, `on.pull_request` e assim por diante) também é bem parecida.

A principal diferença são os jobs pré-empacotados: ao definir `type: build`, o Expo Workflows cuida do ambiente e dos artefatos da build, sem `runs-on` nem etapa de setup para escrever. Vemos isso ao longo do caminho.

> **Nota:** o Expo Workflows pode rodar junto com o GitHub Actions, e um job do GitHub Actions pode disparar um workflow com `eas workflow:run`. Veja [Como integrar o Expo Workflows com o GitHub Actions](https://expo.dev/blog/how-to-integrate-eas-workflows-with-github-actions) para mais informações.
